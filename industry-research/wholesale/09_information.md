## 9-0. なぜ卸売業では情報が重要なのか

### 9-0-1. 卸売業は「情報を売っている」とも言える

`07_goods.md` で見たとおり、卸売業は商品を加工しません。
**入ってくる商品と出ていく商品は同じもの**です。

では、卸売業者が付け加えているものは何か。その大きな部分が**情報**です。

| 卸売業者が持っている情報 | 誰にとっての価値か |
|---|---|
| 「この商品は、今、いくつ、どこにあるか」（在庫情報） | 得意先（すぐ届くか分かる） |
| 「あなたの店にはこの価格で出せます」（得意先別売価情報） | 得意先（仕入原価が分かる） |
| 「来月こういう新商品が出ます」（商品情報・販促情報） | 得意先（品揃えを決められる） |
| 「この地域ではこの商品が伸びています」（販売動向情報） | 仕入先（何を作るか決められる） |
| 「この店は、これくらいの支払能力があります」（与信情報） | 自社（渡してよい金額が分かる） |

> **【Inference】** `01_overview.md` で挙げた卸売業の6機能のうち、
> **「情報提供機能」**はこの章の中心そのものです。
> 残りの5機能（取り揃え・小分け・在庫保有・物流・信用供与）も、
> **それを支える情報が正しくなければ機能しません。**

### 9-0-2. 【最重要】在庫情報が正しくないと、商品は売れない

```
 【在庫情報が正しい場合】

   得意先「醤油50ケースある？」
     ↓
   内勤がシステムを見る → 引当可能在庫 70ケース
     ↓
   「明日お届けできます」 ──▶ 受注成立 ──▶ 出荷 ──▶ 売上


 【在庫情報が実際より少ない場合（実在庫70、システム上30）】

   得意先「醤油50ケースある？」
     ↓
   内勤がシステムを見る → 引当可能在庫 30ケース
     ↓
   「30ケースしか出せません」 ──▶ 得意先は他社に注文する
     ↓
   ★ 倉庫には70ケースあるのに、売れなかった
      （＝在庫は現金化されず、保管コストだけがかかり続ける）


 【在庫情報が実際より多い場合（実在庫30、システム上70）】

   得意先「醤油50ケースある？」
     ↓
   「明日お届けできます」 ──▶ 受注成立
     ↓
   翌日、倉庫でピッキング → **30ケースしかない**
     ↓
   ★ 約束を破ることになる（欠品）
      → 得意先の売場に穴が開く → 信用を損なう
      → 緊急手配・再配送のコストが発生する
```

> **【Inference】** つまり、
> **倉庫に商品が実際にあること**と、**それが売れること**は別の条件です。
> 「売れる在庫」であるためには、**正しい在庫情報が伴っていなければなりません。**
> これが「卸売業では情報が商品そのものと同じくらい重要」と言われる理由です。

## 9-2. 取引の前に用意される情報（マスタ）

**用語**
**マスタ（マスタデータ）**
→ 業務を処理するための**土台となる基本情報**。あらかじめ登録しておき、繰り返し使います。
→ 実務例：商品マスタに「醤油1L、入数12、常温、賞味期限540日」と登録しておけば、
　受注入力のときに商品コードを打つだけで、これらの情報が自動的に付いてきます。

> **【Inference】** マスタが間違っていると、**その商品・その得意先のすべての取引が間違います。**
> 1件の受注ミスは1件で済みますが、マスタのミスは**気づくまで全件に波及します。**

### 9-2-1. 商品情報（商品マスタ）

| 項目 | 内容 |
|---|---|
| **誰が作るか** | 受注・業務機能（マスタ管理担当）。元になる情報は仕入先メーカーから提供される |
| **元になるもの** | メーカーの**商品規格書**、商品案内、JANコード、荷姿情報 |
| **中身** | 商品コード、商品名、メーカー名、JANコード／ITFコード、入数（ケースあたり本数）、荷姿、寸法・重量、温度帯、賞味期限日数、標準仕入価格、標準売価、ロケーション、取扱開始日・終了日、アレルゲン・原材料（食品の場合） |
| **誰が使うか** | 受注・業務（受注入力）、物流（ピッキング・保管）、仕入・調達（発注）、営業（提案）、経理（売上原価） |
| **どこに保管されるか** | 販売管理システムの商品マスタ。元資料（規格書）は商品部でファイル保管【Varies】 |
| **次に何に変わるか** | 受注情報・発注情報・在庫情報の中に**取り込まれて使われる** |
| **頻度** | 案件発生時（新商品導入・規格変更・終売時）／日次（日常の登録作業） |

> **【Typical】** 卸売業では取扱SKUが数千〜数万に達するため、
> 商品マスタの登録・更新が**恒常的に発生する作業**になります。
> モデル企業では約4,500SKUを1名（マスタ管理担当）が管理しています【Example】。

### 9-2-2. 【卸売業の中核】価格情報 ——得意先別売価という複雑さ

#### なぜ複雑なのか

> **卸売業では、同じ商品でも相手によって値段が違います。**
> これが、卸売業の情報管理を他業種より複雑にしている最大の要因です。【Typical】

```
 【同じ「醤油1L（1ケース12本入り）」の売価】【Example：説明用の架空例】

   得意先                        売価      なぜこの価格か
 ─────────────────────────────────────
   Bスーパー（量販・年間1億円）  2,650円   取引量が大きく、条件交渉で決まっている
   C商店（個人商店・月5万円）    2,980円   小口。配送も店先まで
   D飲食店（業務用）             2,850円   毎日配送。まとめ買いはしない
   E給食センター（入札）         2,720円   年度ごとの入札で決まった価格
   F同業卸（二次卸向け）         2,580円   さらに他社へ転売されるため卸価格
   Bスーパー（特売期間中）       2,450円   期間限定の特売価格（メーカーの特売仕切が前提）
```

**なぜ相手によって違うのか**【Typical】

| 理由 | 説明 |
|---|---|
| **取引量が違う** | 大量に買う相手には安く出す。仕入側も大量発注で安く仕入れられる |
| **配送のコストが違う** | 1回2ケースを毎日届ける先と、1回50ケースを週1回届ける先ではコストが違う |
| **取引の歴史がある** | 「開始時に決めた価格」が長年続いていることがある |
| **競合との関係** | 他の卸売業者と競っている得意先には、条件を合わせる必要がある |
| **メーカーの条件が違う** | 特売・販促の対象商品は、メーカーからの仕切自体が期間限定で下がる |
| **建値・掛率の考え方** | 「建値の○掛け」という決め方がされることがある（`12_business-model.md`） |

#### 価格情報の構造

```
 【1つの商品に紐づく価格情報】

  商品コード 001234（醤油1L）
       │
       ├─ 標準売価              2,900円   ← 基準になる価格
       ├─ 得意先別売価
       │    ├─ Bスーパー        2,650円
       │    ├─ C商店            2,980円
       │    ├─ D飲食店          2,850円
       │    └─ …（380社分）
       ├─ 得意先グループ別売価              ← 「量販グループは○円」等【Varies】
       ├─ 期間限定価格（特売価格）
       │    └─ Bスーパー 3/25〜4/5  2,450円
       └─ 数量別価格                       ← 「50ケース以上なら○円」等【Varies】
```

> **【Inference】** 4,500SKU × 380社の組み合わせをすべて個別に持つことは現実的ではないため、
> 実務では「**標準売価を基準に、得意先ごとの掛率や差額で管理する**」
> 「**主要商品と主要得意先の組み合わせだけを個別登録する**」といった形が取られます【Varies】。

#### 価格情報の管理

| 項目 | 内容 |
|---|---|
| **誰が作るか** | 営業機能（売価の決定）＋仕入・調達機能（仕入価格の提示）→ 受注・業務機能（マスタへの登録） |
| **誰が承認するか** | 営業部長（大口・特売は社長）。`06_people.md` §6-5 の #1〜#2 参照 |
| **誰が使うか** | 受注・業務（受注入力時に自動セット）、営業（提案・交渉）、経理（請求）、経営（採算管理） |
| **どこに保管されるか** | 販売管理システムの価格マスタ |
| **次に何に変わるか** | **受注情報の中の「単価」になり、そのまま請求情報の金額になる** |
| **頻度** | 案件発生時（価格改定・特売設定時）／年次（定期の価格見直し）／日次（個別の登録） |

> **【重要】価格情報の誤りは、そのまま請求金額の誤りになります。**
> 受注入力時に価格マスタから自動セットされた単価は、
> 出荷 → 納品 → 売上 → 請求 と、**誰も再計算せずにそのまま流れていきます。**
> だから価格マスタの登録は、卸売業の情報管理の中でも特に慎重に扱われます【Inference】。

#### 特売価格の期間管理

```
 【よくある事故の形】【Example：説明用の架空例】

   3/25〜4/5 の特売価格 2,450円 を登録
     ↓
   4/5 で期限が切れ、4/6 から通常価格 2,650円 に自動で戻る
     ↓
   しかし得意先は「まだ特売期間だと思っていた」
     ↓
   4/6 の納品分について請求金額の認識が食い違う
     ↓
   請求差異として、締め後に発覚する
```

> **【Typical】** 特売価格は**開始日と終了日をセットで登録する**ことが前提になります。
> 終了日を入れ忘れると通常価格に戻らず、逆に早く切れると差異が生じます。

### 9-2-3. 得意先情報（得意先マスタ・納品先マスタ）

| 項目 | 内容 |
|---|---|
| **誰が作るか** | 受注・業務機能（登録）。元情報は営業機能＋与信・債権管理機能 |
| **中身** | 得意先コード、商号、住所、担当者、担当営業、**締め日**、**支払方法・支払サイト**、**与信限度額**、請求書の送付方法・様式、消費税の端数処理、値引条件、リベート条件、取引開始日 |
| **納品先マスタ** | 得意先1社に対して**納品先が複数ある**（4店舗、複数の厨房、複数の現場）。納品先ごとに住所・納品時間・配送コース・荷受担当を持つ |
| **誰が使うか** | 受注・業務（受注入力）、物流（配送コース編成）、経理（請求・入金）、営業（訪問管理） |
| **どこに保管されるか** | 販売管理システムの得意先マスタ |
| **次に何に変わるか** | 受注情報・出荷指示情報・請求情報の中で使われる |
| **頻度** | 案件発生時（新規取引・条件変更・閉店時）／年次（定期見直し） |

> **【重要】「得意先」と「納品先」は別物です。**
> 請求を受ける会社（帳合先）と、商品が届く場所（納品先）は一致しません。
> `16_glossary.md` の「初心者が間違えやすいこと」でも扱います。

### 9-2-4. 仕入先情報・与信情報・配送情報

| 情報 | 誰が作るか | 中身 | 誰が使うか |
|---|---|---|---|
| **仕入先情報** | 仕入・調達機能＋経理 | 仕入先コード、商号、担当者、**締め日・支払サイト**、発注方法（EDI／FAX／Web）、最低発注単位、リードタイム、リベート条件 | 仕入・調達（発注）、物流（入荷予定）、経理（支払） |
| **与信情報** | 与信・債権管理機能 | 与信限度額、設定日、見直し予定日、信用調査の結果、担保・保証の有無 | 受注・業務（与信チェック）、経営（判断）、営業（取引方針） |
| **配送情報（コースマスタ）** | 物流・倉庫機能 | 配送コース、回る順序、担当ドライバー、納品可能時間帯、納品場所の条件（車両制限、荷降ろし設備） | 物流（積込・配送）、受注・業務（納期回答） |

## 9-3. 売る側の情報の連鎖 ——1つの情報が次の情報に変わっていく

> ここが本章の中心です。**情報は形を変えながら次の工程へ渡っていきます。**
> 「作る人」「使う人」「保管場所」「次に何に変わるか」を1つずつ追います。

### 9-3-1. 問い合わせ情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「こういう商品はあるか」「いくらか」「いつ届くか」という得意先からの照会 |
| **誰が作るか** | 得意先（発信元）。受けるのは営業機能または受注・業務機能 |
| **中身** | 商品の特定（メーカー・商品名・規格）、必要数量、希望納期、納品先 |
| **誰が使うか** | 営業（提案）、受注・業務（在庫確認）、仕入・調達（取扱いの可否・納期確認） |
| **どこに保管されるか** | 商談記録、営業日報、システムの問い合わせ履歴【Varies：記録されないことも多い】 |
| **次に何に変わるか** | **見積情報**、または直接**受注情報** |
| **頻度** | 問い合わせ時／日次 |

### 9-3-2. 見積情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「この商品を、この数量なら、この単価で、この納期で出せます」という提示 |
| **誰が作るか** | 営業機能（単価の決定）＋仕入・調達機能（仕入価格・納期の確認） |
| **誰が承認するか** | 営業部長／大口は社長 |
| **中身** | 商品、数量、単価、金額、納期、有効期限、支払条件 |
| **誰が使うか** | 得意先（発注の判断）、内勤（受注時の単価確認）、経理（採算把握） |
| **どこに保管されるか** | 見積書の控え、販売管理システムの見積データ【Varies】 |
| **次に何に変わるか** | 得意先が承諾すれば**受注情報**になる。**見積 ≠ 契約** |
| **頻度** | 問い合わせ時／案件発生時 |

> **【Varies】** 定番品の日常的な取引では、見積を出さずに
> **登録済みの得意先別売価で受注する**ことが一般的です。
> 見積が明示的に出るのは、新規取引・特売・大口・特注品の場合です【Typical】。

### 9-3-3. 【最重要】受注情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「誰が、何を、いくつ、いつ、どこへ、いくらで」という注文の確定内容 |
| **誰が作るか** | 受注・業務機能（内勤）が入力／EDIの場合はシステムが自動生成 |
| **中身** | 受注番号、得意先コード、**納品先コード**、商品コード、数量、**単位（ケース／ボール／バラ）**、単価、金額、希望納品日、備考 |
| **誰が使うか** | 受注・業務（引当）、物流（出荷）、経理（売上・請求）、営業（実績確認）、仕入・調達（補充判断） |
| **どこに保管されるか** | 販売管理システムの受注データ |
| **次に何に変わるか** | **引当情報 → 出荷指示情報 → 納品情報 → 売上情報 → 請求情報** と、一本の線でつながっていく |
| **頻度** | **常時**（受注締切時刻まで受け付け続ける）／**日次**／受注時 |

> **【Inference】** 受注情報は、**この後のすべての情報の親**になります。
> ここで数量・単位・単価・納品先を間違えると、
> 誤出荷・請求違い・在庫のずれが**同時に**発生します。
> `04` §4-2 の S1・S2 で挙げた「ケースとバラの取り違え」「類似商品の取り違え」は、
> この情報の入口で起きる事故です。

#### 【卸売業の特徴】受注チャネルの多様性【Varies】

> 卸売業では、**同じ会社が複数の受注チャネルを同時に運用している**のが普通です。【Typical】

| チャネル | どんな得意先が使うか | 情報の入り方 | 実務上の性質 |
|---|---|---|---|
| **電話** | 個人商店、飲食店、急ぎの追加注文 | 内勤が聞き取ってその場で入力 | 記録が残りにくい。聞き間違いが起きうる。言った・言わないになりやすい |
| **FAX** | 個人商店、中小小売、給食施設 | 受信した紙を見ながら内勤が入力 | 原本が残る。手書きの判読が必要なことがある |
| **EDI** | 食品スーパー、量販店、チェーン本部 | 相手のシステムから自動でデータが届く | 入力不要。大量でも短時間。相手の様式に合わせる必要がある |
| **Web受発注画面** | 中小小売、飲食店 | 得意先が自分で画面に入力 | 入力ミスが得意先側に移る。24時間受付できる |
| **メール** | 小規模先、不定期の注文 | 内勤が読み取って入力 | 形式が統一されず、読み取りに手間がかかる |
| **営業の訪問時の聞き取り** | 個人商店、飲食店 | 営業が手書き伝票やメモに書き、帰社後に入力／モバイル端末で入力 | 現場で在庫が見えないと回答できない |
| **営業のモバイル端末入力** | 同上 | 営業が訪問先でそのまま入力 | 在庫を見ながら受注できる |
| **定期補充（御用聞き）** | 個人商店、飲食店 | 内勤または営業から電話して注文を聞き出す | こちらから働きかける形 |

> **【Inference】** チャネルが多いということは、
> **同じ「受注情報」が、何通りもの経路から同じ1つのデータベースに集まってくる**ということです。
> 経路ごとに処理のしかたが違うため、**受注締切の時刻をどう管理するか**が実務上の論点になります。
> （EDIは自動で入るが、FAXは人が見て入力する時間が必要、など）

### 9-3-4. 引当情報・欠品情報

| 項目 | 引当情報 | 欠品情報 |
|---|---|---|
| **何の情報か** | 「この受注に、この在庫（このロット）を割り当てた」 | 「この受注に対して、在庫がこれだけ足りない」 |
| **誰が作るか** | システムが自動で実行し、受注・業務機能が結果を確認 | システムが引当不足として抽出 |
| **中身** | 受注番号、商品、引当数量、引当ロット、賞味期限、引当日 | 受注番号、商品、不足数量、入荷予定日、代替候補 |
| **誰が使うか** | 物流（ピッキングで期限・ロットの指定に使う）、内勤（出荷可否の判断） | 内勤（対応の起案）、営業（得意先との調整）、仕入・調達（緊急発注） |
| **どこに保管されるか** | 販売管理システムの引当データ | 欠品リスト（システム出力）【Varies】 |
| **次に何に変わるか** | **出荷指示情報** | **欠品連絡 → 変更後の受注情報／緊急発注情報** |
| **頻度** | 日次（受注のつど、自動） | 日次（毎日一定量発生する）【Typical】 |

> **【重要】引当情報は「在庫情報を分割する情報」です。**
> 引当が行われた瞬間、総在庫は「引当済在庫」と「引当可能在庫」に分かれます。
> 得意先に「在庫があります」と答えられるのは**引当可能在庫**の分だけです。

### 9-3-5. 与信判定情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「この受注を出荷してよいか」の判定結果 |
| **誰が作るか** | システム（自動判定）／超過時は与信・債権管理機能と経営機能 |
| **中身** | 得意先、現在の売掛金残高、今回の受注金額、与信限度額、判定結果（可／保留）、承認者 |
| **誰が使うか** | 受注・業務（出荷指示を出すか）、経理（残高管理）、営業（差し戻し時の説明） |
| **どこに保管されるか** | 販売管理システム、与信超過の承認記録 |
| **次に何に変わるか** | **出荷指示情報**（可の場合）／差し戻しの連絡（保留の場合） |
| **頻度** | 日次（受注のつど、自動）／トラブル発生時（超過時の個別判断） |

### 9-3-6. 出荷指示情報・ピッキング指示情報

| 項目 | 出荷指示情報 | ピッキング指示情報 |
|---|---|---|
| **何の情報か** | 「今日、この得意先に、これを出す」という確定した指示 | 「どの棚から、何を、いくつ取るか」という作業レベルの指示 |
| **誰が作るか** | 受注・業務機能（受注締切時に確定） | システムが出荷指示から生成（棚の並び順に並べ替える） |
| **中身** | 出荷日、得意先、納品先、商品、数量、配送コース | ロケーション、商品、数量、ロット・期限の指定、作業者 |
| **誰が使うか** | 物流（作業の割り付け）、内勤（変更受付の可否判断） | ピッキング担当（現場作業） |
| **どこに保管されるか** | 販売管理システム、出荷一覧 | ピッキングリスト（紙）またはハンディターミナルの画面 |
| **次に何に変わるか** | ピッキング指示情報、納品書、配送情報 | 出荷検品情報 |
| **頻度** | 日次（受注締切に1回、または午前・午後の2回など）【Varies】 | 日次 |

> **【Inference】** 出荷指示情報が確定する瞬間が、**その日の受注の締め切り**です。
> ここから先は「注文を受ける情報の世界」から「作業を指示する情報の世界」に変わります。
> 締切後に入った注文は、翌日の出荷指示情報に回ります。

### 9-3-7. 出荷検品情報・配送情報

| 項目 | 出荷検品情報 | 配送情報 |
|---|---|---|
| **何の情報か** | 「指示どおりの商品を、この数だけ、確かに揃えた」という確認の記録 | 「どの車が、どの順で、いつ、どこへ届けるか」 |
| **誰が作るか** | 物流・倉庫機能（出荷検品担当） | 物流・倉庫機能（配送コース編成） |
| **中身** | 出荷番号、商品、検品数量、検品者、検品時刻、バーコード照合の結果 | コース、車両、ドライバー、訪問順、到着予定時刻、個口数 |
| **誰が使うか** | 物流（積込）、内勤（誤出荷時の追跡）、品質・衛生（クレーム時の原因調査） | ドライバー、物流部長、内勤（納期回答） |
| **どこに保管されるか** | WMS（倉庫管理システム）または検品記録【Varies】 | 配車表、運行記録 |
| **次に何に変わるか** | 納品情報 | 納品情報 |
| **頻度** | 日次 | 日次 |

### 9-3-8. 納品情報（受領・検収情報）

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「得意先が、注文どおりの商品を、確かに受け取った」という事実 |
| **誰が作るか** | **得意先**（受領印・検収データ）／記録するのは配送ドライバー・受注業務機能 |
| **中身** | 納品日、納品先、商品、数量、受領者、受領印またはサイン／検収データ |
| **誰が使うか** | 受注・業務（売上確定）、経理（請求の根拠）、営業（クレーム時の確認） |
| **どこに保管されるか** | 受領書（紙）、または得意先から送られる検収データ【Varies】 |
| **次に何に変わるか** | **売上情報** |
| **頻度** | 日次／納品時 |

> **【重要】この情報が、卸売業の情報の流れの中で最も「弱い環」になりやすい部分です。**【Inference】
> 理由は、**この情報を作るのが自社ではなく得意先だから**です。
> - 受領書（紙）が戻ってくるまでに時間がかかる
> - 得意先が受領印を押し忘れる
> - 検収データが得意先のシステムから送られるまでにタイムラグがある
> - **得意先の検収数量と自社の出荷数量が食い違う**（＝請求差異の原因になる）

### 9-3-9. 売上情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「いつ、誰に、何を、いくらで売った」という会計上の事実 |
| **誰が作るか** | 受注・業務機能（確定）／システムが出荷・納品データから自動生成することが多い |
| **中身** | 売上日、得意先、商品、数量、単価、金額、消費税、売上原価、粗利 |
| **誰が使うか** | 経理（締め・請求）、営業（実績管理）、経営（採算管理）、仕入・調達（販売動向の把握） |
| **どこに保管されるか** | 販売管理システムの売上データ → 会計ソフトへ連携【Varies】 |
| **次に何に変わるか** | **締め情報 → 請求情報**／同時に**売掛金の残高情報**になる |
| **頻度** | 日次（売上計上）／納品時 |

> **【重要】いつ売上にするかは、取引条件で決まります。**
> 出荷基準／納品基準／検収基準のどれを採るかで、月末をまたぐ取引の計上月が変わります
> （`04` S10、`08_money.md` 参照）。

### 9-3-10. 締め情報・請求情報

| 項目 | 締め情報 | 請求情報 |
|---|---|---|
| **何の情報か** | 「この期間のこの得意先の売上をこれで確定する」 | 「この金額を、この期日までに支払ってください」 |
| **誰が作るか** | 経理・財務機能（売掛担当） | 経理・財務機能（売掛担当） |
| **中身** | 締め日、得意先、対象期間、売上合計、返品・値引きの反映額 | 請求番号、請求日、得意先、明細、合計金額、消費税、支払期日、振込先、**登録番号（適格請求書の場合）** |
| **誰が使うか** | 経理（請求書作成）、営業（得意先への説明） | 得意先（支払）、経理（債権管理）、与信（残高管理） |
| **どこに保管されるか** | 販売管理システムの締めデータ | 請求書（紙・電子）、請求データ |
| **次に何に変わるか** | 請求情報 | **入金情報**として戻ってくることを期待する情報 |
| **頻度** | 月次（得意先ごとの締め日） | 月次（締め日の後）／請求時 |

> **【Typical】締めの前に「請求差異の確認」が行われます。**
> 得意先の検収データと自社の売上データを突き合わせ、
> 数量・単価・返品の反映に食い違いがないかを確認します。
> ここで見つかった差異は、赤伝や修正伝票で調整してから請求書を出します。

### 9-3-11. 入金情報・消込情報・債権情報

| 項目 | 入金情報 | 消込情報 | 債権情報 |
|---|---|---|---|
| **何の情報か** | 「いつ、誰から、いくら振り込まれたか」 | 「その入金が、どの請求に対応するか」 | 「どの得意先に、いくら残っているか、どれだけ古いか」 |
| **誰が作るか** | 銀行（入出金明細）→ 経理が確認 | 経理・財務機能（売掛担当） | 経理・財務機能（債権担当）／システムが自動集計 |
| **中身** | 入金日、振込名義、金額 | 請求番号、入金額、消込額、差額と原因 | 得意先別売掛金残高、**年齢表**（発生からの経過期間別の内訳） |
| **誰が使うか** | 経理 | 経理、営業（差異の確認依頼） | 与信（限度見直し）、営業（督促）、経営（判断） |
| **どこに保管されるか** | 銀行の入出金明細、会計ソフト | 販売管理システムの消込データ | 売掛金残高表、年齢表 |
| **次に何に変わるか** | 消込情報 | 債権情報（残高） | **与信情報の見直し／督促情報／出荷停止の指示** |
| **頻度** | 月次（得意先の支払日）／入金時 | 日次・月次／入金時 | 月次／常時 |

**用語**
**年齢表（エイジングリスト）**
→ 売掛金を「いつ発生したものか」で区分して並べた表。
→ 実務例：「1か月以内：3,200万円／1〜2か月：480万円／2〜3か月：90万円／3か月超：35万円」。
　**古い売掛金ほど回収が難しくなる**ため、古い区分に残っている金額が注目されます【Typical】。

## 9-4. 買う側の情報の連鎖

### 9-4-1. 【最重要】在庫情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「どの商品が、どこに、いくつ、どのロット・期限であるか」 |
| **誰が作るか** | 物流・倉庫機能（入出庫の実績）＋システム（自動更新） |
| **中身** | 商品コード、ロケーション、**総在庫数**、**引当済数**、**引当可能数**、**入荷予定数**、ロット番号、賞味期限、最終出荷日、在庫金額 |
| **誰が使うか** | **ほぼ全機能**。受注・業務（引当・納期回答）、営業（提案・納期回答）、仕入・調達（発注判断）、物流（ピッキング・保管）、経理（在庫金額・決算） |
| **どこに保管されるか** | 販売管理システムの在庫データ、WMS |
| **次に何に変わるか** | 引当情報、発注点判定情報、棚卸情報、在庫金額（決算資料） |
| **頻度** | **常時**（入出庫のつど自動更新）／日次（確認）／月次・半期・年次（棚卸で照合） |

> **【最重要】在庫情報には4つの数字がある。**
>
> ```
>  総在庫（実在庫）     100ケース   ← 倉庫に実際にある数
>  − 引当済在庫          30ケース   ← すでに他の注文に割り当て済み
>  ────────────────────
>  = 引当可能在庫        70ケース   ← 新しい注文に使える数 ★ これが「売れる在庫」
>  + 入荷予定           170ケース   ← 発注済みでまだ届いていない数
> ```
>
> 得意先に「在庫はありますか」と聞かれたとき、答えの根拠になるのは
> **引当可能在庫**（今日出せる分）と**入荷予定**（後日出せる分）です。
> 総在庫だけを見て答えると、他の注文の分まで約束してしまうことになります。

### 9-4-2. 発注点判定情報・仕入発注情報

| 項目 | 発注点判定情報 | 仕入発注情報 |
|---|---|---|
| **何の情報か** | 「この商品は発注すべき水準まで減った」 | 「この仕入先に、これを、いくつ、いつまでに」 |
| **誰が作るか** | システムが候補を自動抽出 → 仕入・調達機能（バイヤー）が判断 | 仕入・調達機能（バイヤー） |
| **中身** | 商品、引当可能在庫、入荷予定、発注点、安全在庫、直近の出荷実績、推奨発注数 | 発注番号、仕入先、商品、数量、仕入単価、希望納期、**納品先（自社倉庫か直送先か）** |
| **誰が使うか** | 仕入・調達（発注判断）、在庫管理 | 仕入先、物流（入荷予定の準備）、受注・業務（納期回答） |
| **どこに保管されるか** | 発注候補リスト | 販売管理システムの発注データ、注文書 |
| **次に何に変わるか** | 仕入発注情報 | **入荷予定情報 → 入荷情報 → 仕入情報** |
| **頻度** | 日次（日々の補充判定）／週次・月次（定番の見直し） | 日次（補充発注）／受注時（都度仕入）／トラブル発生時（緊急発注） |

### 9-4-3. 入荷予定情報・入荷情報・仕入情報

| 項目 | 入荷予定情報 | 入荷情報（検品情報） | 仕入情報 |
|---|---|---|---|
| **何の情報か** | 「いつ、何が、いくつ届く予定か」 | 「実際に何がいくつ届き、検品の結果どうだったか」 | 「いくらで仕入れたという会計上の事実」 |
| **誰が作るか** | 発注データから自動生成 | 物流・倉庫機能（入荷担当） | 経理・財務機能／入荷データから自動計上 |
| **中身** | 入荷予定日、仕入先、商品、数量 | 入荷日、商品、実入荷数、**賞味期限**、**ロット番号**、破損の有無、発注との差異 | 仕入日、仕入先、商品、数量、仕入単価、金額、消費税 |
| **誰が使うか** | 物流（受入準備）、内勤（納期回答）、仕入（進捗確認） | 在庫管理（在庫更新）、仕入（差異の照会）、品質・衛生（期限・ロットの記録） | 経理（買掛・支払）、仕入（仕入実績）、経営（採算） |
| **どこに保管されるか** | 販売管理システムの入荷予定データ | 検品記録、WMS、入荷実績データ | 販売管理システムの仕入データ → 会計ソフト |
| **次に何に変わるか** | 入荷情報 | **在庫情報（引当可能在庫が増える）**、仕入情報 | **買掛情報 → 支払情報**、**リベート情報の集計対象** |
| **頻度** | 発注時 | 日次／入荷時 | 日次／納品時 |

> **【重要】入荷情報は「在庫情報に変わる情報」です。**
> 検品して入庫が登録された瞬間に、その商品は**引当可能在庫として売れる状態**になります。
> 逆に、現物は届いているのに入庫登録が済んでいなければ、
> **倉庫にあるのに売れない**状態になります（9-0-2 の1つ目のパターン）。

### 9-4-4. 買掛情報・支払情報・リベート情報

| 項目 | 買掛情報 | 支払情報 | リベート情報 |
|---|---|---|---|
| **何の情報か** | 「どの仕入先に、いくら払う義務があるか」 | 「いつ、いくら、どう払ったか」 | 「条件をどれだけ達成し、いくら受け取る／支払うか」 |
| **誰が作るか** | 仕入データから自動生成 | 経理・財務機能（買掛担当） | 仕入・調達機能（条件の把握と合意）＋経理（計上） |
| **中身** | 仕入先別買掛金残高、締め日、支払予定日 | 支払日、仕入先、金額、支払方法（振込・手形・でんさい） | 契約条件、対象期間、対象仕入高・販売高、達成率、リベート額、精算方法 |
| **誰が使うか** | 経理（支払準備）、経営（資金繰り） | 仕入先、経理、経営 | 経理（損益への反映）、仕入（交渉）、経営（実績評価） |
| **どこに保管されるか** | 販売管理システム、会計ソフト | 会計ソフト、支払明細 | 仕入先との取り決め書、精算資料【Varies】 |
| **次に何に変わるか** | 支払情報 | 資金繰りの実績 | **リベート収入（または販売促進費）として損益に反映** |
| **頻度** | 月次（仕入先ごとの締め日） | 月次（支払日） | 四半期／半期／年次／月次（契約による）【Varies】 |

## 9-5. 仕入先から得意先へ流れる情報 ——商品情報・販促情報

### 9-5-1. なぜこの流れが重要なのか

> 卸売業者は、**モノを運ぶだけでなく、情報も運んでいます。**
> メーカーが持っている商品の情報は、そのままでは小売店に届きません。
> 全国に数万軒ある小売店1軒ずつにメーカーが説明して回ることはできないためです。

```
 【商品情報・販促情報の流れ】

  メーカー（商品部・営業）
    │  新商品情報、規格書、販促計画、価格改定の予告、CM・チラシの予定
    │  展示会・商談会での商品説明
    ▼
  卸売業者のバイヤー（商品部）
    │  取扱いの判断、仕入価格の交渉、自社としての推奨商品の選定
    │  自社の販促企画への落とし込み
    ▼
  卸売業者の営業（外勤）
    │  「この新商品、御社の客層に合うと思います」
    │  「来月から値上げになります。今のうちに」
    │  「このチラシ企画に乗りませんか」
    ▼
  得意先（小売店の店主・バイヤー、飲食店の料理長）
    │  採用の判断、発注量の決定、売場づくり、メニュー変更
    ▼
  消費者
```

### 9-5-2. 流れる情報の種類

| 情報 | 中身 | 得意先にとっての意味 |
|---|---|---|
| **新商品情報** | 発売日、規格、価格、特徴、想定客層、CM予定 | 品揃えに加えるかを判断する材料 |
| **商品規格書** | 原材料、アレルゲン、栄養成分、保存方法、賞味期限 | 食品表示・アレルギー対応のために必要（法令対応の根拠になる） |
| **販促情報** | チラシ企画、店頭販促物（POP）、増量パック、キャンペーン | 売場企画を組み立てる材料 |
| **価格改定情報** | 改定日、改定幅、対象商品 | 仕入原価と店頭価格の見直しが必要になる |
| **商品改廃情報** | 終売（生産終了）、リニューアル、パッケージ変更 | 発注の切替、在庫の売り切り判断 |
| **供給情報** | 生産の遅れ、原料不足、出荷調整 | 代替品の検討、事前の確保 |
| **回収（リコール）情報** | 対象ロット、回収理由、対応方法 | **即座の対応が必要**。売場からの撤去 |

### 9-5-3. 逆向きにも流れる ——得意先から仕入先へ

```
  得意先（売場・厨房）
    │  「この商品は動きが悪い」「この規格が欲しい」「この価格では売れない」
    │  「他社のこの商品が伸びている」「こういうクレームがあった」
    ▼
  卸売業者の営業
    │  営業日報、商談記録、クレーム記録として社内に持ち帰る
    ▼
  卸売業者のバイヤー
    │  自社の販売実績データとして集計
    ▼
  メーカー
       商品開発、生産計画、販促計画に使う
```

> **【Inference】** メーカーにとって、**卸売業者は「市場で何が起きているか」を教えてくれる情報源**です。
> `01_overview.md` の「情報提供機能」は双方向であり、
> 卸売業者は**上流にも下流にも情報を渡している**ことになります。

### 9-5-4. POSデータの受領【Varies】

**用語**
**POSデータ（ポスデータ）**
→ 小売店のレジ（POSレジ）で記録される「**いつ、何が、いくつ、いくらで売れたか**」のデータ。
→ 実務例：スーパーが自社のPOSデータを取引先の卸売業者に提供し、
　卸売業者はそれを見て「どの商品が売場で実際に動いているか」を把握します。

> **【Varies】** POSデータが卸売業者に提供されるかどうかは、
> 得意先の方針・取引関係・業態によって大きく異なります。
> 提供される場合、卸売業者は「**自社が納品した数（出荷）**」だけでなく
> 「**実際に消費者に売れた数（販売）**」を知ることができ、
> 補充提案や販促提案の根拠に使われます【Typical】。
>
> 提供されない場合、卸売業者が持っているのは自社の出荷実績だけであり、
> **得意先の売場で在庫が積み上がっているのか、売れて減っているのかは分かりません。**

## 9-6. 例外時に発生する情報

| 情報 | 誰が作るか | 中身 | 誰が使うか | 次に何に変わるか |
|---|---|---|---|---|
| **返品情報** | 営業（受付）→内勤（伝票）→物流（現物） | 返品日、得意先、商品、数量、**返品理由**、責任の所在、現物の状態 | 経理（請求調整）、在庫管理（在庫修正）、仕入（仕入先返品）、品質（原因分析） | 赤伝（売上のマイナス）、在庫情報の修正、仕入先への返品情報 |
| **クレーム情報** | 営業（一次受付） | 発生日、得意先、商品、内容、**ロット番号**、原因、対応、再発防止 | 品質・衛生、物流、仕入・調達、経営 | 対応記録、仕入先への申し入れ、（重大時）回収情報 |
| **回収（リコール）情報** | 品質・衛生機能（仕入先からの連絡を受けて） | 対象商品、対象ロット、回収理由、出荷先リスト | 全機能、得意先、行政 | **出荷先の特定 → 得意先への連絡 → 現物の回収** |
| **棚卸情報** | 物流（実地カウント）＋在庫管理・経理（照合） | 実地棚卸数、帳簿在庫数、差異、差異の原因 | 経理（決算）、経営（在庫状況） | 修正後の在庫情報、在庫金額（決算資料） |
| **滞留在庫情報・期限接近情報** | 在庫管理機能（システムが抽出） | 商品、在庫数、最終出荷日、経過日数、賞味期限、残存日数、在庫金額 | 仕入・調達（処置判断）、営業（販売努力）、経理（評価損） | 処置の記録、値下げ販売、返品交渉、廃棄損の計上 |
| **誤出荷情報** | 物流または得意先からの指摘 | 出荷日、正しい商品／実際に出した商品、数量、原因 | 物流、内勤、営業、経理 | 再出荷、赤伝、在庫修正 |

> **【Inference】** これらの情報に共通するのは、
> **「正常な流れから外れた事実を記録する情報」**であることです。
> 記録が漏れると、**在庫情報と帳簿在庫がずれ、売掛金残高が実態と合わなくなり、
> 棚卸や消込の段階で必ず問題として表面化します。**

## 9-7. 情報が「変換される」ポイント

> 卸売業の情報の流れを一言でいえば、**「同じ事実が形を変えながら流れていく」**ことです。
> どこで形が変わるかを整理します。

| 変換の場所 | 何から何へ | 誰が変換するか | 変換で何が加わるか |
|---|---|---|---|
| **受注入力** | 注文（言葉・紙・データ）→ **受注情報** | 内勤／EDIは自動 | 商品コード、単価、納品先コードが付く |
| **在庫引当** | 受注情報 → **引当情報** | システム | ロット・賞味期限が特定される |
| **出荷指示の確定** | 引当情報 → **出荷指示情報** | 内勤（締切の判断） | 出荷日・配送コースが確定する |
| **ピッキングリスト生成** | 出荷指示情報 → **作業指示** | システム | 棚の並び順に並べ替えられる |
| **納品・検収** | 出荷 → **納品情報** | **得意先** | 「受け取った」という相手方の確認が付く |
| **売上計上** | 納品情報 → **売上情報** | システム／内勤 | 会計上の事実になる。売掛金が発生する |
| **締め** | 売上情報の集計 → **請求情報** | 経理 | 期間でまとめられ、返品・値引きが反映される |
| **消込** | 入金情報 × 請求情報 → **債権情報** | 経理 | どの請求が回収済みかが確定する |
| **入庫** | 入荷情報 → **在庫情報** | 物流／システム | ロケーションが付き、**売れる在庫になる** |
| **棚卸** | 現物 → **修正後の在庫情報** | 物流・経理 | 帳簿と現物のずれが解消される |

## 9-8. 業種による情報の違い【Level 2】

| 比較軸 | **食品卸** | **建材卸** | **機械・工具卸** | **医薬品卸** | **アパレル卸** |
|---|---|---|---|---|---|
| **受注チャネルの中心** | EDI（量販）＋電話・FAX（個店・飲食） | 電話・FAX・メール（工務店） | **型番検索を伴う問い合わせ**が受注の前段に必ず入る | EDI・専用の受発注システム【Varies】 | 展示会・展示受注、期中はWeb・電話 |
| **商品情報の重さ** | **規格書・アレルゲン・栄養成分**が法令対応に直結 | 規格・認定番号・寸法・施工条件 | **型番・図面・仕様書・互換情報**が膨大 | **添付文書・ロット・期限**が法令上の要請 | 品番×色×サイズ、素材表示 |
| **在庫情報の粒度** | 商品 × ロット × 賞味期限 × 温度帯 | 商品 × 寸法 × 色番 × ロット | 商品 × 型番 × 版数 | 商品 × ロット × 使用期限 × 保管条件 | 品番 × 色 × サイズ（SKUが爆発的に増える） |
| **価格情報の複雑さ** | 得意先別売価＋特売価格＋リベート | **案件別の見積価格**が中心 | 代理店価格体系＋案件別値引 | **公的価格制度**が前提にある | 掛率（上代に対する掛け目）で管理されることが多い |
| **納期情報** | 「明日の朝」が基本。日次で完結 | **工事の工程に合わせた日時指定** | 在庫品は即納、機械は数週間〜数か月 | 当日・翌日。緊急配送の要請がある | シーズン投入日が全店で揃う |
| **トレーサビリティ** | 回収に備えたロット追跡 | ロット差・色ムラの追跡 | 型番の版数管理 | **法令に基づく記録の保存** | 限定的 |

## この章のまとめ

1. 卸売業では、**「情報」を抽象語のままにせず、何の情報かを名指しして追う**ことが理解の鍵になる。
2. 取引の前に **マスタ（商品・価格・得意先・仕入先・与信・配送）** が揃っていなければ、
   1件の受注も処理できない。
3. **在庫情報が正しくないと商品は売れない。** 少なく見えれば売り逃し、多く見えれば欠品になる。
   在庫情報には**総在庫／引当済／引当可能／入荷予定**の4つの数字があり、
   「売れる在庫」は**引当可能在庫**である。
4. 卸売業の情報管理を複雑にしている最大の要因は、**得意先別売価**である。
   同じ商品でも相手により価格が違い、期間限定価格も重なる。
5. 受注情報は**この後のすべての情報の親**。受注チャネルは電話・FAX・EDI・Web・メール・
   訪問時の聞き取りなど多様で、同じ会社に共存している【Varies】。
6. **納品情報（受領・検収）は、自社ではなく得意先が作る情報**であるため、
   情報の流れの中で最も遅れやすく、ずれやすい。
7. メーカーの**商品情報・販促情報は、バイヤー → 営業を経て得意先に届く**。
   逆方向にも売場の情報が流れており、卸売業者は上流と下流の双方に情報を渡している。

→ 次は `10_documents.md` で、これらの情報が**どんな紙・データの形をとるか**を見ます。
