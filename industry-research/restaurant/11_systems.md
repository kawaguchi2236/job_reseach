## 11-0 飲食業のシステムの全体像

### 道具の置かれ方

```
                     【本部】
        ┌──────────────────────────────────┐
        │  会計ソフト     給与計算ソフト      │
        │  表計算ソフト   インターネットバンキング │
        │  原価管理の仕組み（`【Varies】`）      │
        └──────────┬───────────────────────┘
                   │ 売上データ・勤怠データ・仕入データ
                   ↕
        ┌──────────┴───────────────────────┐
        │              【店舗】                │
        │                                     │
        │   ┌──────────────────────────┐      │
        │   │      POSレジ（中心）        │      │

        │   │  メニュー別出数を記録する    │      │
```

### 飲食業のシステムの特徴

| # | 特徴 | 内容 |
|---|---|---|
| 1 | **POSレジが情報の中心にある** | `【Typical】` 会計の処理と同時に、売上・客数・メニュー別出数が記録されます。多くの数字がここから出ます |
| 2 | **接客しながら使う道具がある** | `【Typical】` ハンディ端末・決済端末は、客の前で操作する道具です。事務所で使う道具とは性格が違います |
| 3 | **社外の会社の画面を使う仕事がある** | `【Typical】` グルメサイト・デリバリープラットフォーム・卸のWeb発注画面は、店が自分で持っている仕組みではありません |
| 4 | **紙と併用されている** | `【Typical】` 予約台帳、仕込み表、衛生管理の記録表、オーダー伝票は、紙で運用されている例が多くみられます（`【Varies】`） |

## 11-1 POSレジ

| 項目 | 内容 |
|---|---|
| **正式名称・読み方** | POS（ピーオーエス）レジ。POS＝Point of Sales（販売時点） |
| **何を管理するものか** | **会計を処理し、その時点で「誰に・何が・いくつ・いくらで」売れたかを記録する**仕組み |
| **誰が使うか** | ⑪レジ・会計機能（ホール担当・店長）／⑩ホール機能／⑦店長機能／④経理・財務機能（データを受け取る側） |
| **どの業務で使うか** | A-4 開店準備（動作確認・釣銭）／A-5 来店・案内（客数・テーブルの入力）／A-6 注文（オーダーの記録）／A-9 会計／A-11 締め作業／A-13 日報 |
| **どんな情報が入るか** | 商品マスタ（品名・売価・**税区分**）／テーブル番号・客数／注文内容と数量／割引・クーポン／決済手段／受領額／`【Varies】` 店内飲食かテイクアウトかの区分 |
| **どんな情報が出るか** | レシート／会計伝票／**レジ精算票（日計表）**／売上高／客数・組数／客単価／**メニュー別の出数**／時間帯別の売上／決済手段別の内訳／割引・訂正・返金の記録 |
| **頻度** | `常時`（営業中）／`日次`（締め処理） |

### なぜPOSが飲食業の中心になるのか

`【Inference】` POSは「会計を早く正確にする道具」であると同時に、
**「売上データを作る道具」**でもあります。

```
 会計をする（A-9）
    ↓
 その処理の副産物として、次が自動的に記録される
    ・いつ（時間帯）
    ・何が（メニュー別の出数）
    ・いくつ
    ・いくらで
    ・何人の客に（客数）
    ・どの決済手段で
    ↓
 この記録が、翌日の発注と仕込みを決める材料になる（`09_information.md` 9-14）
```

> **用語：出数（でかず）**
> → そのメニューが**何皿売れたか**の数。
> → 実務例：「先月の牛すじ煮込みの出数は320」。
> → **なぜ重要か：** 出数が分からないと、①翌日の仕込み量の根拠がない、
> 　②メニューの見直しの判断ができない、
> 　③原価率が上がった原因がどのメニューにあるか追えません
> 　（`05_departments.md` ① E-7）。

### 消費税の区分

`【Fact】` 消費税の税率は、消費税法第29条により、
軽減対象課税資産の譲渡等については100分の6.24、それ以外については100分の7.8と定められています。
`【Fact】` 軽減対象となる「飲食料品の譲渡」からは、
**飲食店業その他の政令で定める事業を営む者が行う食事の提供**
（テーブル、椅子、カウンターその他の飲食に用いられる設備のある場所において飲食料品を
飲食させる役務の提供をいい、**当該飲食料品を持帰りのための容器に入れ、又は包装を施して行う譲渡は、
含まないものとする**。）が除かれます（消費税法別表第一第1号イ）。

`【Typical】` したがって、店内飲食とテイクアウトの両方を扱う店では、
**会計時にこの区分を入力する**形が採られます。
`【Fact】` レシートの記載事項については、消費税法第57条の4第2項が適格簡易請求書の記載事項を定めています。

### POSを使わない場合

`【Typical】` 中小飲食企業では、POSレジを使わず、
**手書きの伝票と、金額を打つだけのレジ（金銭登録機）**で運営している店もあります（`【Varies】`）。
`【Inference】` この場合、メニュー別の出数は**伝票を数えるか、記憶に頼る**ことになります。
`【Typical】` 実務では、その日の伝票をまとめて集計する、
日報に「出た数」を書き留める、といった形で情報が残されます。

> `【Fact】` 本資料は、どちらの方法についても良し悪しの評価を行いません。
> **情報の流れとして見たときに、「メニュー別の出数という情報が、どこかで作られ、翌日に使われる」
> という構造は共通しています**（`09_information.md` 9-14）。

## 11-2 ハンディターミナル（オーダーエントリー端末）

| 項目 | 内容 |
|---|---|
| **正式名称・読み方** | ハンディターミナル、ハンディ端末、オーダーエントリー端末（現場では「ハンディ」） |
| **何を管理するものか** | **客の注文を、その場で入力し、厨房とPOSに同時に伝える**道具 |
| **誰が使うか** | ⑩ホール機能 |
| **どの業務で使うか** | A-6 注文（オーダー）／A-8 提供（追加注文の入力） |
| **どんな情報が入るか** | テーブル番号／客数／品名と数量／**アレルギー・食材の除去の指定**／焼き加減・辛さ等の指定／提供タイミングの希望 |
| **どんな情報が出るか** | **厨房のプリンタに出る注文伝票**（→⑨キッチン機能）／POSへの売上予定データ（→⑪レジ・会計機能） |
| **頻度** | `受注時`（営業中に随時） |

### 何のための道具か

`【Inference】` ハンディ端末は、**1回の入力で2つの場所に情報を送る**道具です。

```
 ホール担当が入力
     ↓
  ┌──┴──┐
  ↓        ↓
厨房      POS
（作る）  （会計に使う）
```

`【Typical】` これに対し、手書きの伝票では、
**厨房用の控えと会計用の控えを分けて書く**、または伝票を厨房から会計へ回す、という形になります。

### オーダーの通し方の比較（情報の伝わり方として）

`【Typical】` 注文をホールから厨房へ伝えることを「**オーダーを通す**」と言います。
`【Varies】` 伝え方は店により異なります。

| 方式 | 使う道具 | 情報の伝わり方 |
|---|---|---|
| **口頭＋復唱** | なし | ホールが声で伝え、厨房が復唱する。`【Typical】` 記録は残らない |
| **手書き伝票** | 伝票用紙 | 伝票に書いて厨房に差す。`【Typical】` 紙が残るため後から確認できる |
| **ハンディ端末＋キッチンプリンタ** | ハンディ端末、キッチンプリンタ | 入力と同時にPOSに記録され、厨房で伝票が出る |
| **テーブルオーダー用タブレット** | タブレット | **客が自分で入力する**。ホールの入力作業が発生しない |
| **モバイルオーダー** | 客のスマートフォン | 同上。`【Varies】` 店が用意した画面を客が自分の端末で開く |
| **券売機** | 券売機 | **先に代金を受け取り、注文を確定させる**。食券が厨房への指示になる |

> `【Fact】` 本資料はこれらの方式について良し悪しの評価を行いません。
> `【Inference】` 情報の流れとして見ると、どの方式でも
> 「**オーダー情報が⑩ホール機能側で作られ、⑨キッチン機能に渡り、⑪レジ・会計機能でも使われる**」
> という構造は同じです（`09_information.md` 9-7）。

## 11-3 キッチンプリンタ／キッチンディスプレイ

| 項目 | 内容 |
|---|---|
| **何を管理するものか** | **ホールで入力された注文を、厨房で見える形にする**道具 |
| **誰が使うか** | ⑨キッチン機能 |
| **どの業務で使うか** | A-7 調理 |
| **どんな情報が入るか** | ハンディ端末・タブレット・POSから送られたオーダー情報 |
| **どんな情報が出るか** | **紙の注文伝票**（キッチンプリンタ）／**画面上の注文一覧**（キッチンディスプレイ `【Varies】`） |
| **頻度** | `常時`（営業中） |

> **厨房が受け取ったあと、何をするか**
> `【Inference】` 厨房は、受け取ったオーダーをそのまま実行するのではなく、
> **複数のオーダーを同時に見ながら、逆算して作り始める順番を決めます**
> （`09_information.md` 9-8、`04_end-to-end-process.md` A-7）。
> `【Typical】` 紙の伝票の場合は、伝票を並べ替えることでこの作業を行います。
> `【Varies】` キッチンディスプレイでは、画面上で注文の進行を管理する形になります。

`【Typical】` 中小飲食企業では、**手書きの伝票を厨房に差す**方式も広く使われています（`【Varies】`）。

## 11-4 予約管理システム／予約台帳

| 項目 | 内容 |
|---|---|
| **何を管理するものか** | **予約を記録し、席の空きを管理する**仕組み |
| **誰が使うか** | ⑩ホール機能／⑦店長機能／⑧仕込み機能（仕込み量の根拠として見る） |
| **どの業務で使うか** | A-P 予約管理／A-4 開店準備（席割り）／A-5 来店・案内／A-1 発注・A-3 仕込み（数量の根拠） |
| **どんな情報が入るか** | 日時／人数／氏名／連絡先／コース・飲み放題の希望／席の希望／**アレルギー等の要望**／予約の経路（電話・サイト・店頭） |
| **どんな情報が出るか** | **当日の予約一覧**／席の空き状況／予約件数・予約人数／`【Varies】` 予約の経路別の集計 |
| **頻度** | `常時`／`問い合わせ時` |

### 紙の予約台帳との併用

`【Typical】` 中小飲食企業では、**紙の予約台帳**で運用している店も多くみられます（`【Varies】`）。
`【Inference】` 予約が入る経路が複数ある（電話、予約サイト、店頭、自社サイト）ため、
**どの経路から入った予約も、最終的に1つの場所にまとまっている必要があります。**
`【Typical】` 紙の台帳を1冊に決めて、サイト経由の予約も転記する、という運用が採られることがあります。

> **予約情報が正しくまとまっていないと何が起きるか**
> `【Inference】`
> - 同じ時間帯に予約を取りすぎて、席が足りなくなる
> - 予約が入っていることに気づかず、席を他の客に使ってしまう
> - 仕込み量の根拠がずれる
> - **アレルギーの要望が厨房に届かない**
>
> `【Typical】` だから予約を受けた時点で台帳に書き、
> 当日の朝に改めて厨房とホールで共有する、という二重の流れになります
> （`04_end-to-end-process.md` A-4）。

## 11-5 グルメサイト・予約サイトの店舗管理画面

| 項目 | 内容 |
|---|---|
| **何を管理するものか** | **店の掲載内容（客が見る情報）と、そこから入る予約を管理する**画面。`【Typical】` 店が持っている仕組みではなく、**社外の事業者が提供する画面**です |
| **誰が使うか** | ⑥販促機能（代表取締役・店長）／⑩ホール機能（予約の確認） |
| **どの業務で使うか** | 掲載内容の管理／予約の受付枠の設定／口コミへの対応／A-P 予約管理 |
| **どんな情報が入るか** | 店舗情報（店名・住所・電話・**営業時間・定休日**）／メニューと価格／写真／紹介文／予約を受け付ける枠（日時・人数）／クーポンの設定 |
| **どんな情報が出るか** | 予約情報／客の問い合わせ／口コミ／`【Varies】` 閲覧数・予約数などの実績 |
| **頻度** | `月次`または`案件発生時`（掲載内容の更新）／`常時`（予約の受付）／`問い合わせ時`（口コミ対応） |

> **なぜ掲載内容の更新が業務になるのか**
> `【Typical】` 客が店を探す入口はグルメサイト・地図アプリ・SNSに移っています
> （`02_industry-structure.md` 11-1(3)）。
> `【Inference】` **掲載情報（営業時間・定休日・メニュー・写真）が古いままだと、
> 来店の機会を失います**（`03_company-structure.md` 3-3⑥）。
> さらに、掲載内容と実際の提供内容・価格が違う場合は、別の問題が生じます
> （`15_rules-customs.md` の景品表示法の項を参照）。

`【Varies】` 掲載料・予約手数料の体系は事業者と契約内容により異なり、
公表されていない場合もあるため、本資料では具体的な金額・率を示しません。

## 11-6 デリバリープラットフォームの店舗用端末・管理画面

| 項目 | 内容 |
|---|---|
| **何を管理するものか** | **アプリ経由で入った注文を受け取り、調理して配達員に渡すまでを管理する**仕組み。`【Typical】` **社外の事業者が提供する端末・画面**です |
| **誰が使うか** | ⑨キッチン機能（注文の受け取り）／⑩ホール機能（受け渡し）／⑥販促機能（掲載商品・価格の設定）／④経理・財務機能（入金と手数料の確認） |
| **どの業務で使うか** | 注文の受付／調理／受け渡し／掲載商品の設定／受付の一時停止 |
| **どんな情報が入るか** | 掲載商品と価格（`【Varies】` 店内と異なる価格を設定する場合がある）／営業状況・受付の可否／調理にかかる時間の目安 |
| **どんな情報が出るか** | **注文情報**（品目・数量・受け渡し時刻）／配達員の到着予定／`【Varies】` 売上と手数料の明細／入金予定 |
| **頻度** | `常時`（営業中） |

### 店から見た構造（店内飲食との違い）

`【Typical】` 2020年前後から、アプリ経由で注文を受け、
プラットフォーム事業者が手配した配達員が客まで運ぶ販売形態が一般化しました
（`02_industry-structure.md` 11-6(5)）。

| | 店内飲食 | デリバリープラットフォーム経由 |
|---|---|---|
| 客と店の接点 | 店の中で直接 | **アプリの画面の中**（店は客と会わない） |
| 席を使うか | 使う | **使わない** |
| 容器 | 店の食器（洗って再利用） | **使い捨て容器**（都度コストが発生） |
| 代金の受け取り | その場で店が受け取る | **プラットフォームが受け取り、後日店へ送金** |
| 手数料 | なし（決済手数料を除く） | **売上に対して手数料が発生** `【Varies】` |

`【Varies】` **手数料率・契約条件・入金サイクルは事業者と契約内容により異なり、
公表されていない場合もあるため、本資料では具体的な数値を示しません。**

> **営業中の操作として何が発生するか**
> `【Inference】` 店内が混雑しているときに配達の注文が重なると、
> 厨房の処理が追いつかなくなります。
> `【Typical】` そのため、**受付を一時的に停止する**操作が管理画面で行われます。
> これは店内営業における「止め」（`09_information.md` 9-7）と同じ性質の判断です。

| **何を管理するものか** | **発注内容を仕入先に伝え、発注の記録を残す**仕組み |
| **誰が使うか** | ⑦店長機能／②仕入・調達機能 |

### 発注の伝え方は多様

`【Typical】` 中小飲食企業では、発注の手段が取引先ごとに違うことが一般的です（`【Varies】`）。

|---|---|---|

> **発注の記録がないと何が困るか**
> `【Inference】` 届いたものが「注文どおりか」を確認できません。
> 検品（A-2）は「発注情報と現物を突き合わせる」作業だからです
> （`10_documents.md` 10-1）。
> `【Varies】` 中小飲食企業では、手書きのメモが発注控として機能している例もあります。

`【Fact】` 本資料は、どの発注手段についても良し悪しの評価を行いません。

## 11-9 勤怠管理・シフト管理

### (1) 勤怠管理

| 項目 | 内容 |
|---|---|
| **何を管理するものか** | **誰が、いつからいつまで働いたか**を記録し、労働時間を集計する仕組み |
| **誰が使うか** | 従業員本人（打刻）／⑤人事・労務機能（集計）／⑦店長機能（確認） |
| **どの業務で使うか** | 勤怠管理・集計／給与計算 |
| **どんな情報が入るか** | 出勤・退勤の時刻／休憩の時間／欠勤・遅刻・早退 |
| **どんな情報が出るか** | 個人別の労働時間／**深夜（午後10時から午前5時まで）の時間**／時間外労働の時間／勤務表（勤怠集計表） |
| **頻度** | `常時`（打刻）／`月次`（集計） |

`【Fact】` 使用者が、午後10時から午前5時まで（厚生労働大臣が必要であると認める場合においては、
その定める地域又は期間については午後11時から午前6時まで）の間において労働させた場合においては、
その時間の労働については、通常の労働時間の賃金の計算額の2割5分以上の率で計算した
割増賃金を支払わなければなりません（労働基準法第37条第4項）。
`【Inference】` したがって勤怠の記録は、**深夜の時間帯を分けて集計できる必要があります。**

`【Varies】` 中小飲食企業では、**紙のタイムカード**を使っている店も多くみられます（`【Typical】`）。

### (2) シフト管理

| 項目 | 内容 |
|---|---|
| **何を管理するものか** | **誰をいつ働かせるかの予定を作る**仕組み |
| **誰が使うか** | ⑦店長機能（作成）／従業員本人（希望の提出・確認）／⑤人事・労務機能（人件費の枠） |
| **どの業務で使うか** | シフトの作成と当日の欠員対応 |
| **どんな情報が入るか** | 各人の勤務可能な日・時間帯（希望）／必要な人数と時間帯（②客数見込み情報から）／人件費の枠／`【Fact】` 労働基準法上の制約（労働時間・休憩・休日） |
| **どんな情報が出るか** | **シフト表**／予定されている人件費／人数の過不足 |
| **頻度** | `週次`または`月次`（`【Varies】`）／`トラブル発生時`（当日の欠員） |

`【Varies】` 中小飲食企業では、表計算ソフトや手書きのシフト表を使っている店も多くみられます（`【Typical】`）。
`【Typical】` シフトの連絡・欠員の連絡には、電話やメッセージアプリが使われます。

> **シフトを組むときに関わる法令**
> `【Fact】` 使用者は、労働者に、休憩時間を除き1週間について40時間を超えて労働させてはならず、
> 1週間の各日については、休憩時間を除き1日について8時間を超えて労働させてはなりません
> （労働基準法第32条）。
> `【Fact】` 使用者は、労働時間が6時間を超える場合においては少なくとも45分、
> 8時間を超える場合においては少なくとも1時間の休憩時間を労働時間の途中に
> 与えなければなりません（同法第34条第1項）。
> `【Fact】` 使用者は、労働者に対して、毎週少なくとも1回の休日を与えなければなりません（同法第35条第1項）。

## 11-12 温度記録の仕組み

| 項目 | 内容 |
|---|---|
| **何を管理するものか** | **冷蔵庫・冷凍庫の温度、加熱・冷却の温度を測り、記録する**道具 |
| **誰が使うか** | ⑧仕込み機能・⑨キッチン機能・⑫清掃・衛生機能（記録する人）／⑦店長機能（食品衛生責任者。確認する人） |
| **どの業務で使うか** | A-2 納品・検品（納品時の温度）／A-3 仕込み／A-7 調理（加熱の中心温度）／A-4 開店準備・A-12 清掃・衛生記録（冷蔵庫・冷凍庫の温度） |
| **どんな情報が入るか** | 測定した温度／測定の日時／測定者／異常があった場合の対応 |
| **どんな情報が出るか** | **温度記録表**（衛生管理の実施記録の一部）／`【Varies】` 異常時の通知 |
| **頻度** | `日次`／`常時`（`【Varies】` 店が作成した衛生管理計画で定めた頻度による） |

### 形態は多様

| 形態 | 内容 |
|---|---|
| **紙の記録表** | `【Typical】` 中小飲食企業では、記録表を紙で運用している例が多くみられます（`【Varies】`） |
| 温度計＋記録アプリ・タブレット（`【Varies】`） | 測った値を端末に入力し、保存する |
| 温度を自動で記録する機器（`【Varies】`） | 冷蔵庫の温度を継続的に記録する |

### 制度上の位置づけ

`【Fact】` 食品衛生法第51条第1項は、営業施設の衛生的な管理その他公衆衛生上必要な措置について、
厚生労働省令で、①施設の内外の清潔保持、ねずみ及び昆虫の駆除その他一般的な衛生管理に関すること
（第1号）、②食品衛生上の危害の発生を防止するために特に重要な工程を管理するための取組
（小規模な営業者その他の政令で定める営業者にあっては、その取り扱う食品の特性に応じた取組）に
関すること（第2号）の基準を定めることとしています。
`【Fact】` 同条第2項により、営業者はこれらの基準に従い、公衆衛生上必要な措置を定め、
これを遵守しなければなりません。
`【Fact】` 食品衛生法施行規則第66条の2第3項第3号は、
**衛生管理の実施状況を記録し、保存すること**を定めています
（保存期間は、取り扱う食品が使用・消費されるまでの期間を踏まえ合理的に設定する）。

> `【Inference】` したがって温度記録の道具は、
> 「温度を測るため」だけでなく**「測ったという事実を残すため」**の道具でもあります
> （`09_information.md` 9-13、`10_documents.md` 10-6）。
> `【Varies】` どの工程の温度を、どの頻度で記録するかは、
> 店が作成した衛生管理計画の内容によります。

## 11-14 中小飲食企業における紙と電子の併用（事実の記述）

`【Typical】` 中小飲食企業では、次のような状態が広くみられます。
**以下は実態の記述であり、評価や推奨ではありません。**

| 場面 | 電子で行われている例 | 紙・口頭で行われている例 |
|---|---|---|
| 会計 | POSレジ | `【Varies】` 金銭登録機＋手書きの伝票 |
| オーダー | ハンディ端末＋キッチンプリンタ／タブレット | **手書きの伝票を厨房に差す** |
| 予約 | 予約管理システム／予約サイトの管理画面 | **紙の予約台帳** |
| 発注 | 卸のWeb発注画面／発注システム | **電話・FAX・営業担当者への口頭** |
| 仕込み | `【Varies】` アプリ・表計算 | **手書きの仕込み表** |
| 衛生管理の記録 | `【Varies】` アプリ・自動記録の機器 | **紙の記録表** |
| 勤怠 | 勤怠管理システム | **紙のタイムカード・出勤簿** |
| シフト | シフト管理システム／表計算 | **手書きのシフト表** |
| 日報 | 表計算・アプリ | **紙の日報** |
| 経理 | 会計ソフト | `【Typical】` 紙の帳票を税理士に渡す形 |

> **なぜ併用が生じるのか（構造の説明）**
> `【Inference】` 飲食店では、1つの店の中に性格の違う場所が同居しています。
> - **客の前**（ホール・レジ）：客を待たせない速さが要る
> - **厨房**：水・油・熱があり、手が濡れている
> - **事務所**：落ち着いて数字を扱える
>
> これに加えて、社外の事業者が提供する画面（グルメサイト、デリバリープラットフォーム、
> 卸のWeb発注画面）も使います。
> `【Inference】` **これらが1つの仕組みにまとまっているとは限らないため、
> 場面ごとに道具が分かれる**、という構造になります。
>
> `【Fact】` 本資料は、この状態について良し悪しの評価を行わず、
> 改善の提案も行いません。
