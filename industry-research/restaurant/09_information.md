# 09_information.md — 飲食業の「情報の流れ」

> このファイルは `common/methodology.md` §6 の定義に従い、**情報**の流れを扱います。
> §6 は「『情報』という抽象語で終わらせない。具体的に何の情報かを命名する」ことを求めています。
> 本章では**12種類の情報に名前を付け**、それぞれについて
> **誰が作り／誰が使い／どこに保管され／次に何に変わるか**を追います。
> 機能番号（①〜⑫）は `03_company-structure.md` 3-2、
> 工程番号（A-1〜A-13、B-1〜B-6 ほか）は `04_end-to-end-process.md` に対応します。
> 帳票そのもの（様式・記載事項）は `10_documents.md`、
> 情報を扱う道具は `11_systems.md` で扱います。
> 出典の詳細は `19_sources.md` を参照してください。

## 9-0 飲食業の情報が持つ3つの特徴

| # | 特徴 | 内容 |
|---|---|---|
| 1 | **情報が短時間で次の形に変わる** | `【Inference】` 「オーダー情報」は数分後には「調理指示情報」になり、数十分後には「会計情報」になります。製造業の生産計画のように、同じ情報が数週間残ることはまれです |
| 2 | **伝達の誤りがその場で損失になる** | `【Inference】` オーダーが正しく伝わらなければ、違う料理が作られ、食材が無駄になり、客を待たせます。翌日に直すことはできません |
| 3 | **記録が法令上の義務になっているものがある** | `【Fact】` 衛生管理の実施状況の記録・保存は、食品衛生法施行規則第66条の2第3項第3号に定めがあります |

> `【Inference】` つまり飲食業の情報は、
> **「速く正確に渡す情報」**と**「残して後で使う情報」**の2種類に分かれます。
> 前者はオーダー情報・調理指示情報、後者は日報情報・衛生管理記録・原価情報です。
> 本章ではこの2つを区別しながら整理します。

## 9-1 情報の流れの全体像

```
                  ┌──── 【客・社外から入る情報】 ────┐
                  │                                 │
          ①予約情報               客からの注文（口頭）  相場・入荷の情報（卸から）
                  │                                 │
                  ↓                                 │
          ②客数見込み情報 ←─── ⑪原価情報・過去の売上データ
                  │                                 │
        ┌─────────┴─────────┐                       │
        ↓                   ↓                       │
   ③発注情報            ⑤仕込み指示情報 ←────────────┘
        │                   │
        ↓                   │
   ④納品情報               │
   （納品書・検品記録）      │
        │                   ↓
        │              【仕込み品ができる】
        │                   │
        │                   ↓
        │              ⑥オーダー情報 ←── 客からの注文
        │                   │
        │                   ↓
        │              ⑦調理指示情報
        │                   │
        │                   ↓
        │              ⑧提供情報
        │                   │
        │                   ↓
        │              ⑨会計情報 ──→ POSに記録される
        │                   │
        │          ┌────────┴────────┐
        │          ↓                 ↓
        │     ⑩日報情報         ⑫衛生管理記録
        │          │            （温度・健康・清掃）
        │          ↓                 │
        └────→ ⑪原価情報             │
                   │                 │
                   ↓                 ↓
           【本部 ④経理・財務機能】  【店内に保存】
           店別損益・FL比率         保健所の求めに応じて提示
                   │
                   ↓
           翌月以降の②客数見込み情報・③発注情報へ戻る
```

### 12種類の情報の一覧（早見表）

| # | 情報の名前 | 誰が作るか | 誰が使うか | どこに保管されるか | 次に何に変わるか |
|---|---|---|---|---|---|
| ① | **予約情報** | ⑩ホール機能・⑦店長機能 | ⑦⑧⑨⑩ | 予約台帳／予約管理システム | ②客数見込み情報 |
| ② | **客数見込み情報** | ⑦店長機能 | ⑦⑧⑤ | `【Varies】` 店長の手元・シフト表・仕込み表 | ③発注情報／⑤仕込み指示情報／シフト |
| ③ | **発注情報** | ⑦店長機能 | 仕入先（社外） | 発注控／発注システム | ④納品情報 |
| ④ | **納品情報** | 仕入先（社外）＋⑦⑨（検品結果） | ⑧⑨④ | 納品書ファイル／検品記録 | 在庫情報／仕入の記録（B-3） |
| ⑤ | **仕込み指示情報** | ⑦店長機能・調理責任者 | ⑧仕込み機能 | 仕込み表 | 仕込み実績情報／仕込み品 |
| ⑥ | **オーダー情報** | ⑩ホール機能（客の注文から） | ⑨キッチン機能・⑪レジ・会計機能 | POS／注文伝票 | ⑦調理指示情報／⑨会計情報 |
| ⑦ | **調理指示情報** | ⑨キッチン機能（オーダーを組み替えたもの） | ⑨キッチン機能の内部 | キッチンプリンタの伝票／キッチンディスプレイ／口頭 | ⑧提供情報 |
| ⑧ | **提供情報** | ⑨キッチン機能 | ⑩ホール機能 | `【Typical】` デシャップでの口頭・伝票 | （提供の完了） |
| ⑨ | **会計情報** | ⑪レジ・会計機能 | 客・④経理・財務機能 | POS／レシート／会計伝票 | ⑩日報情報／売上データ |
| ⑩ | **日報情報** | ⑦店長機能 | ④経理・財務機能・代表取締役 | 日報（紙／表計算／アプリ `【Varies】`） | ⑪原価情報／店別損益 |
| ⑪ | **原価情報** | ④経理・財務機能 | 代表取締役・①メニュー開発機能・⑦店長機能 | 会計ソフト／表計算 | 売価の見直し／②客数見込み情報へ戻る |
| ⑫ | **衛生管理記録** | ⑧⑨⑫（実施した人）／確認は⑦店長機能 | ⑦店長機能（食品衛生責任者）・保健所 | `【Fact】` 記録し保存する（施行規則第66条の2第3項第3号） | 検証・計画の見直し（同項第4号） |

## 9-2 ① 予約情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「いつ・何名・どんな内容で来店するか」が確定している情報 |
| **誰が作るか** | ⑩ホール機能（電話・店頭での受付）／⑦店長機能（大口・法人の予約）／`【Typical】` 予約サイト経由では客自身が入力 |
| **中身** | 日時／人数／連絡先／コース・飲み放題の希望／席の希望／**アレルギー等の要望**／特別な事情（記念日、車椅子の利用など `【Varies】`） |
| **誰が使うか** | ⑦店長機能（発注・シフト）／⑧仕込み機能（仕込み量）／⑨キッチン機能（コース内容）／⑩ホール機能（席割り） |
| **どこに保管されるか** | `【Typical】` 予約台帳（紙）または予約管理システム（`【Varies】`）／グルメサイト・予約サイトの管理画面 |
| **次に何に変わるか** | **②客数見込み情報**（その日に何人来るかの土台）→ ③発注情報・⑤仕込み指示情報・シフト |
| **頻度** | `常時`／`問い合わせ時` |

> **予約情報が飲食業の計画の土台になる理由**
> `【Inference】` 飲食業は「何人来るか分からない」商売です。
> しかし予約が入っている分だけは、**来る人数・食べるもの・時間が確定します。**
> つまり予約は、**仕入量・仕込み量・シフト人数を決めるための唯一の確定情報**です
> （`04_end-to-end-process.md` A-P）。

> **予約情報が正しく伝わらないと何が起きるか**
> `【Inference】`
> - 席が用意されていない → 客が待つ／断ることになる
> - 仕込みが足りない → コースが出せない
> - アレルギーの要望が厨房に届かない → **客の健康に関わる**
> - 人数の聞き違い → 席の割り当てと仕込み量の両方がずれる
>
> `【Typical】` だから予約を受けた時点で台帳に書き、
> 当日の朝に改めて厨房とホールで共有する、という二重の流れになります
> （`04_end-to-end-process.md` A-4）。

## 9-3 ② 客数見込み情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「その日、何人くらい来そうか」という**見込み**の情報。確定情報ではない |
| **誰が作るか** | ⑦店長機能 |
| **中身** | 予約で確定している人数／予約以外に来そうな人数の見込み／時間帯ごとの偏りの見込み |
| **何をもとに作るか** | ①予約情報（確定）／**前週の同曜日の実績**／**前年の同時期の実績**／天気予報／曜日／近隣のイベント／`【Varies】` 過去の来店傾向 |
| **誰が使うか** | ⑦店長機能（発注量・シフト）／⑧仕込み機能（仕込み量）／⑤人事・労務機能（人件費の枠との突き合わせ） |
| **どこに保管されるか** | `【Varies】` 明示的な帳票にならないことも多い（店長の手元のメモ、仕込み表の欄、シフト表に反映される） |
| **次に何に変わるか** | **③発注情報**／**⑤仕込み指示情報**／シフト表 |
| **頻度** | `日次` |

> **この情報は「作られたことに気づきにくい」情報です**
> `【Inference】` ①予約情報や⑨会計情報と違って、客数見込み情報は
> **帳票として明確に残らないことが多い**のが特徴です。
> しかし発注量も仕込み量もシフト人数も、すべてこの見込みから決まっています。
> `【Typical】` 中小飲食企業では、この見込みが**店長の頭の中にある**状態が一般的です
> （`【Varies】`）。

> `【Example】`（説明用の架空例）モデル企業A店の店長が、翌日の見込みを立てる場面。
> 「明日は金曜。夜の早い時間に12名の予約が1件、4名の予約が2件。
> 　先週の同曜日の夜の客数は68名。天気は晴れ。
> 　→ 予約で20名が確定。飛び込みを含めて夜は70名前後と見る」
> この「70名前後」が客数見込み情報です。
> **これが外れると、発注も仕込みもシフトも同時にずれます。**

## 9-4 ③ 発注情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「どの仕入先に、何を、いくつ、いつ届けてもらうか」 |
| **誰が作るか** | ⑦店長機能（`【Varies】` 中小では店主・調理責任者が行う場合もある） |
| **中身** | 仕入先／品目／数量／納品希望日 |
| **何をもとに作るか** | 在庫の残量／②客数見込み情報／本部が決めた仕入先と単価（②仕入・調達機能から）／仕入先ごとの発注締切時刻／相場・欠品の情報 |
| **誰が使うか** | 仕入先（社外）／④経理・財務機能（後で納品書・請求書と突き合わせる） |
| **どこに保管されるか** | `【Varies】` 発注控（紙）／発注システム・卸のWeb発注画面の履歴／`【Typical】` 電話・FAXの場合は記録が残らないこともある |
| **次に何に変わるか** | **④納品情報**（翌日以降、モノと納品書が届く） |
| **頻度** | `日次`（生鮮）／`週次`（乾物・調味料・消耗品 `【Varies】`）／`発注時` |

> **発注情報が残らないと何が困るか**
> `【Inference】` 発注の記録がないと、届いたものが「注文どおりか」を確認できません。
> 検品（A-2）は「発注情報と現物を突き合わせる」作業だからです。
> `【Typical】` 電話で口頭発注した場合、店側に控えがなければ、
> 数量の食い違いが起きたときに何が正しかったのかを示せません。
> `【Varies】` 中小飲食企業では、手書きのメモが発注控として機能している例もあります。

## 9-5 ④ 納品情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「何が、いくつ、いくらで届いたか」＋「その状態はどうだったか」 |
| **誰が作るか** | **仕入先**（納品書）＋**店**（検品の結果） |
| **中身** | 仕入先／納品日／品目／数量／単価／金額／（店が加える）検品の結果・返品や不足の有無・温度の確認結果 |
| **誰が使うか** | ⑧仕込み機能・⑨キッチン機能（使える在庫として）／④経理・財務機能（B-3 仕入計上、B-5 請求書照合） |
| **どこに保管されるか** | `【Typical】` 納品書ファイル（店の事務所）→ 本部へ回す／温度の記録は衛生管理の記録へ |
| **次に何に変わるか** | 在庫情報／**仕入の記録（買掛金）**（B-3）→ B-4 締め → B-5 請求書照合 → B-6 支払 |
| **頻度** | `日次`（生鮮）／`納品時` |

> **1つの行為から2つの情報が生まれる**
> `【Inference】` 納品・検品は現場では1回の行為ですが、
> **モノの側（使える在庫になった）と書類の側（仕入として記録される）に分かれます**
> （`04_end-to-end-process.md` 4-3、`07_goods.md` 7-3）。

> **初心者がつまずく点：納品書 ≠ 請求書**
> - **納品書**＝「これを届けました」という、モノに添えられる書類。**届いた都度**もらう
> - **請求書**＝「この期間分の合計はこれです」という、お金を請求する書類。**締めた後**にもらう
>
> `【Typical】` 飲食業では毎日納品があるため、納品書は毎日たまり、請求書は月に1枚来る形になります
> （`【Varies】` 締めのサイクルは取引先により異なります）。

> **検品結果というひと手間**
> `【Example】`（説明用の架空例）納品書に「トマト3kg」とあるが、1つに傷みがある場合、
> Sさん（店長）は納品書に「トマト1個返品」とメモします。
> `→ このメモがないと、月末の請求書照合（B-5）で「返品した分も請求されている」ことに気づけません。`
> **検品結果は、納品情報に店が付け加える情報**です。

## 9-6 ⑤ 仕込み指示情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「今日、何を、どれだけ仕込むか」 |
| **誰が作るか** | ⑦店長機能または調理責任者 |
| **中身** | 品目／仕込む量／優先順位／`【Varies】` 使う食材の指定（先入先出で古いものから） |
| **何をもとに作るか** | ②客数見込み情報／①予約情報（コース内容・アレルギー）／前日の仕込み品の残量／④納品情報（何が届いたか、何が届かなかったか）／レシピ（①メニュー開発機能から） |
| **誰が使うか** | ⑧仕込み機能（調理社員・キッチン担当） |
| **どこに保管されるか** | `【Typical】` 仕込み表（`【Varies】` 手書きの用紙である例が多くみられます）／口頭での指示 |
| **次に何に変わるか** | **仕込み実績情報**（実際に何をどれだけ仕込んだか）／仕込み品（モノ） |
| **頻度** | `日次`（`【Varies】` 品目により`週次`のものもある） |

> **仕込み指示が「情報」として重要な理由**
> `【Inference】` 仕込み量の判断は、その日の利益を左右します
> （多く仕込めば廃棄、少なく仕込めば品切れ。`07_goods.md` 7-6）。
> **その判断の内容と結果が記録されていないと、翌週に同じ判断をするときの材料がありません。**
> `【Typical】` だから仕込み表には「計画（いくつ仕込む）」と「実績（いくつ仕込んだ・いくつ残った）」の
> 両方を書く形が採られます（`05_departments.md` ⑧ E-9、`10_documents.md`）。

> **④納品情報が⑤仕込み指示情報を変える例**
> `【Example】`（説明用の架空例）レタスが1ケース未着だった場面。
> → 「本日のサラダはキャベツのサラダに変更」という判断が生まれる
> → 仕込み指示が「レタスの洗浄・カット」から「キャベツの千切り」に変わる
> → さらにホールへ「サラダの内容が変わった」という情報が渡る（A-4 の情報共有）
> → メニューブックの内容と違うため、客への説明が必要になる
>
> `【Inference】` **1つの欠品情報が、仕込み・メニュー・接客の3つに波及しています。**

## 9-7 ⑥ オーダー情報 ── 飲食業でもっとも重要な情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「どのテーブルの客が、何を、いくつ、どういう条件で注文したか」 |
| **誰が作るか** | ⑩ホール機能（客の口頭の注文を受けて）／`【Varies】` セルフ業態では客自身（券売機・タブレット・モバイルオーダー） |
| **中身** | テーブル番号／品名／数量／**アレルギー・食材の除去の指定**／焼き加減・辛さ等の指定／**提供のタイミングの希望**／客数 |
| **誰が使うか** | ⑨キッチン機能（作るため）／⑪レジ・会計機能（会計に使うため） |
| **どこに保管されるか** | POS（電子）／注文伝票（紙）／`【Varies】` 口頭のみの場合は記録が残らない |
| **次に何に変わるか** | **⑦調理指示情報**（厨房が作業の順に組み替える）／**⑨会計情報**（そのテーブルの合計金額） |
| **頻度** | `受注時`（営業中に随時） |

### オーダーの「通し方」（飲食業固有の作法）

`【Typical】` 注文をホールから厨房へ伝えることを「**オーダーを通す**」と言います。
伝え方には主に次の形があります（`【Varies】` 店により異なる）。

| 方式 | どう伝わるか | 情報として見たときの特徴 |
|---|---|---|
| **口頭＋復唱** | ホールが厨房に声で伝え、厨房が復唱する | `【Typical】` 小規模店で使われる。**記録が残らない** |
| **手書き伝票** | 伝票に書き、厨房に差す | `【Typical】` **紙が残るため後から確認できる** |
| **ハンディ端末＋キッチンプリンタ** | ホールが端末に入力→厨房のプリンタから伝票が出る | `【Typical】` **入力と同時にPOSに記録される**（⑨会計情報が自動でできる） |
| **タブレット／モバイルオーダー** | 客が自分で入力する | `【Typical】` 聞き間違いが起きない。ホールの作業が減る |

`【Typical】` 中小飲食企業では、**手書きの伝票を厨房に差す**方式も広く使われています（`【Varies】`）。
`【Fact】` 本資料はこれらの方式について良し悪しの評価を行いません。

### ★ オーダーがキッチンに正確に伝わらないと何が起きるか

`【Inference】` 誤りの型ごとに、起きることが違います。

| 誤りの型 | 何が起きるか | どこに損失が出るか |
|---|---|---|
| **通し忘れ**（伝わっていない） | 料理が作られない。客は待ち続ける。呼ばれて初めて気づく | 客の不満／席の回転が止まる／`【Typical】` 詫びとして値引き・サービスをすることがある |
| **二重通し**（同じ注文が2回入る） | 同じ料理が2つ作られる。1つは出せない | **食材のロス**（`07_goods.md` 7-9 の「提供ロス」） |
| **品名の間違い** | 違う料理が作られる。作り直しになる | 食材のロス＋提供の遅れ |
| **数量の間違い** | 足りない／余る | 追加で作る時間／余った分のロス |
| **テーブル番号の間違い** | 別のテーブルに出てしまう | 下げて作り直し。`【Inference】` 客が口をつけていれば廃棄 |
| **特記事項の脱落**（焼き加減・辛さ・取り分け） | 希望と違うものが出る | 作り直し／客の不満 |
| **★アレルギー情報の脱落** | **除去すべき食材が入ったまま提供される** | `【Inference】` **客の健康に直接影響する。ほかの誤りとは性質が違う** |
| **品切れの情報が逆方向に伝わっていない** | 出せないものの注文を受けてしまう | 客に謝って注文を取り直す（`04_end-to-end-process.md` A-4） |

> **なぜ「復唱」するのか**
> `【Inference】` 注文の聞き間違い・伝え間違いは、
> ①違う料理を作る（食材のロス）、②客を待たせる（作り直し）、③客の不満、を同時に引き起こします。
> **アレルギーの聞き漏らしは、客の健康に直接影響します。**
> 復唱は、この誤りを**提供前に**発見するための工程です
> （`04_end-to-end-process.md` A-6）。

> **アレルギー情報だけ扱いが違う理由**
> `【Typical】` 客からアレルギーの申し出があった場合、ホールは必ず厨房に伝え、
> 厨房は使用食材と調理器具の使い回しを確認します。
> `【Inference】` これは接客の丁寧さの問題ではなく、**客の生命に関わる情報伝達**です。
> **伝達経路が曖昧な店では事故が起こり得ます**（`03_company-structure.md` 3-4⑩）。
> `【Typical】` そのため、伝票への明示（「卵除去」等）、提供時の口頭確認（「こちらが卵除去です」）という
> **二重の確認**が行われます。

> **「通し」に関する飲食業の用語**
> - **一括（いっかつ）で通す**＝注文をまとめて厨房へ渡すこと
> - **追加オーダー**＝食事の途中で追加される注文。**客単価を押し上げる要素**
> - **止め（とめ）**＝厨房が一時的に注文を受けられない状態にすること（作業が詰まったとき）
> - **番手（ばんて）**＝提供の順番

## 9-8 ⑦ 調理指示情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「どの料理を、どの順番で、いつ作り始めるか」──**オーダー情報を作業の順に組み替えたもの** |
| **誰が作るか** | ⑨キッチン機能（厨房の中で） |
| **中身** | 作る順序／担当（誰が何を作るか）／火入れの開始タイミング／同時に仕上げるべき組み合わせ |
| **誰が使うか** | ⑨キッチン機能の内部（調理社員→キッチン担当への指示を含む） |
| **どこに保管されるか** | `【Typical】` キッチンプリンタから出た伝票を並べる／キッチンディスプレイ（`【Varies】`）／口頭のやりとり |
| **次に何に変わるか** | **⑧提供情報**（料理が完成し、ホールに渡る） |
| **頻度** | `常時`（営業中） |

> **なぜ「オーダー情報」と「調理指示情報」を分けるのか**
> `【Inference】` **オーダーの順番と、作り始める順番は同じではありません。**
> 料理によって調理時間がバラバラだからです。
>
> `【Example】`（説明用の架空例）4名のテーブルから
> 「刺身盛り（3分）／だし巻き玉子（8分）／唐揚げ（10分）／牛すじ煮込み（3分）」が一括で通った場合。
> 同時に出すなら、**唐揚げを最初に、次にだし巻き、最後に刺身と煮込みを仕上げる**、
> という逆算になります。
> **注文順に作ると、料理がバラバラに出てしまいます**（`04_end-to-end-process.md` A-7）。
>
> `【Inference】` つまり厨房は、受け取ったオーダー情報をそのまま実行するのではなく、
> **複数のオーダーを同時に見ながら、逆算して作り始める順番を決める**という
> 情報の加工を行っています。これが飲食業の調理の難しさの中心です。

`【Typical】` さらに厨房は、**同じテーブルの料理をできるだけ同時に出す**ことと、
**先に注文した客より後の客に先に出さない**ことの両方を満たす必要があります。
`【Inference】` 複数テーブルのオーダーが重なると、この組み替えの難度が上がります。
ピーク時に「止め」の判断が出るのは、この組み替えが追いつかなくなったときです。

## 9-9 ⑧ 提供情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「この料理は、どのテーブルの、誰のものか」 |
| **誰が作るか** | ⑨キッチン機能（完成を知らせるとき） |
| **中身** | テーブル番号／料理名／**特記事項がある場合はその内容**（「こちらが卵除去」など）／取り皿の要否 |
| **誰が使うか** | ⑩ホール機能（運ぶ人） |
| **どこに保管されるか** | `【Typical】` 保管されない。**デシャップでの口頭と伝票のやりとりで消える**（`【Varies】`） |
| **次に何に変わるか** | （提供の完了）→ 追加注文があれば⑥オーダー情報へ戻る／なければ⑨会計情報へ |

> **保管されない情報も「情報の流れ」の一部です**

> とくにアレルギー対応品の場合、誰の前に置くかを誤ると健康被害につながり得ます。
> `【Typical】` だから実務では、デシャップという場所を決め、テーブル番号を声で言い合い、
> 提供時にもう一度口頭で確認する、という形が採られます（`06_people.md` 6-4）。

## 9-10 ⑨ 会計情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「そのテーブルの客が、何をいくつ食べ、合計いくら支払ったか、どの手段で支払ったか」 |
| **誰が作るか** | ⑪レジ・会計機能 |
| **中身** | 注文内容と数量／合計金額／割引・クーポンの適用／**決済手段**（現金／クレジットカード／電子マネー／コード決済）／客数／`【Varies】` 店内飲食かテイクアウトかの区分 |
| **誰が使うか** | 客（レシート）／④経理・財務機能（売上データ）／⑦店長機能（A-11 締め作業） |
| **どこに保管されるか** | POS（電子）／会計伝票／レシート・領収書の控え |
| **次に何に変わるか** | **⑩日報情報**（当日の集計）／売上データ（メニュー別出数を含む）／⑪原価情報の分母（売上高） |
| **頻度** | `入金時`（営業中に随時） |

### 会計情報が持つ「2つの顔」

`【Inference】` 会計情報は、**その場で使う情報**と**後で使う情報**の両方です。

| 顔 | 内容 | 使う人 |
|---|---|---|
| **その場で使う** | 客に金額を伝え、代金を受け取り、釣銭を渡す | ⑪レジ・会計機能・客 |
| **後で使う** | 売上高／客数／客単価／**メニュー別の出数**／決済手段別の内訳／時間帯別の売上 | ④経理・財務機能／①メニュー開発機能／⑦店長機能 |

> **メニュー別の出数（でかず）が後で効いてくる**
> **出数（でかず）**
> → そのメニューが**何皿売れたか**の数。
> → 実務例：「先月の牛すじ煮込みの出数は320」。
> → **なぜ重要か：** 出数が分からないと、
> 　①翌日の仕込み量の根拠がない、②メニューの見直しの判断ができない、
> 　③原価率が上がった原因がどのメニューにあるか追えません
> 　（`05_departments.md` ① E-7）。
> `【Typical】` POSレジは、会計を処理すると同時にこの出数を記録しています。

### 消費税の区分（店内飲食とテイクアウト）

`【Fact】` 消費税の税率は、消費税法第29条により、
軽減対象課税資産の譲渡等については100分の6.24、それ以外については100分の7.8と定められています。
`【Fact】` 軽減対象となる「飲食料品の譲渡」から、
**飲食店業その他の政令で定める事業を営む者が行う食事の提供**
（テーブル、椅子、カウンターその他の飲食に用いられる設備のある場所において飲食料品を
飲食させる役務の提供をいい、**当該飲食料品を持帰りのための容器に入れ、又は包装を施して行う譲渡は、
含まないものとする**。）は除かれます（消費税法別表第一第1号イ）。

> `【Inference】` したがって会計情報には、
> **店内飲食か持ち帰りかという区分**を含める必要が生じます。
> `【Typical】` POSでは、会計時にこの区分を入力する形が採られます（`11_systems.md`）。

`【Fact】` レシートの発行については、消費税法第57条の4第2項が適格簡易請求書の記載事項を定めています。

> `【Inference】` 売上・客数という数字だけでは、なぜそうなったかが分かりません。
> 「台風で予約が3件キャンセルになった」「エアコンが故障して客席が暑かった」
> 「レタスが未着でメニューを差し替えた」といった事実が併記されて初めて、
> 数字の意味が読めます。
> `【Typical】` だから日報には、数値欄と特記事項欄の両方が置かれます（`10_documents.md`）。

## 9-12 ⑪ 原価情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「その期間に、食材費がいくらかかり、売上に対して何％だったか」 |
| **誰が作るか** | ④経理・財務機能 |
| **中身** | 当月の食材費／原価率／FL比率・FLR比率／`【Varies】` メニュー別の理論原価と実際原価の差 |
| **何をもとに作るか** | ⑩日報情報（売上高）／④納品情報→B-3 仕入計上（仕入額）／**A-I 棚卸の結果（月初・月末の在庫）**／A-L 廃棄記録 |
| **誰が使うか** | 代表取締役（経営判断）／①メニュー開発機能（売価とレシピの見直し）／⑦店長機能（発注・仕込みの見直し） |
| **どこに保管されるか** | 会計ソフト／表計算（店別損益表・月次試算表） |
| **次に何に変わるか** | 売価の見直し／仕入先の見直し／仕込み量の判断材料 → **②客数見込み情報・③発注情報へ戻る** |
| **頻度** | `月次`（`【Varies】` 棚卸の頻度に依存する） |

### なぜ棚卸がないと原価情報が作れないのか

`【Typical】` その月の食材費（売上原価）は、**仕入れた金額そのものではありません。**

```
当月の食材費 ＝ 月初の在庫 ＋ 当月の仕入 − 月末の在庫
```

> `【Example】`（説明用の架空例。数値は説明のための仮置きです）
> 月初在庫60万円、当月仕入180万円、月末在庫70万円なら、
> 当月の食材費＝60＋180−70＝**170万円**。
> 売上が500万円なら原価率は34.0％。仕入額180万円で計算すると36.0％となり、2ポイントずれます
> （`04_end-to-end-process.md` A-I）。

### 原価情報が「原因」まで遡れるかどうかは、記録の質で決まる

`【Inference】` 原価率が上がったとき、見るべき場所は複数あります。

```
原価率が上がった
   │
   ├─ 仕入単価が上がった？ → ④納品情報（単価）・②仕入・調達機能
   ├─ 捨てた量が増えた？   → A-L 廃棄記録（理由の分類）
   │     ├─ 仕入ロス   → ③発注情報（発注量）
   │     ├─ 仕込みロス → ⑤仕込み指示情報（仕込み量）
   │     └─ 提供ロス   → ⑥オーダー情報（伝達の誤り）
   ├─ 売れるメニューの構成が変わった？ → ⑨会計情報（メニュー別出数）
   └─ 棚卸の数え漏れ／記録漏れ？ → A-I 棚卸
```

> `【Inference】` **記録がなければ、原価率という結果の数字だけが残り、原因が分かりません。**
> A-L で「なぜ捨てたのか」まで記録する理由がここにあります
> （`04_end-to-end-process.md` A-L、`07_goods.md` 7-9）。

## 9-13 ⑫ 衛生管理記録 ── なぜ残すのか

### 制度の根拠（条文）

`【Fact】` 食品衛生法第51条第1項は、営業施設の衛生的な管理その他公衆衛生上必要な措置について、
厚生労働省令で次の2つの事項に関する基準を定めることとしています。

| 号 | 基準の内容 | 省令上の定め |
|---|---|---|
| 第1号 | 施設の内外の清潔保持、**ねずみ及び昆虫の駆除**その他**一般的な衛生管理**に関すること | `【Fact】` 食品衛生法施行規則第66条の2第1項・**別表第17** |
| 第2号 | 食品衛生上の危害の発生を防止するために特に重要な工程を管理するための取組（**小規模な営業者その他の政令で定める営業者**にあっては、その**取り扱う食品の特性に応じた取組**）に関すること | `【Fact】` 食品衛生法施行規則第66条の2第2項・**別表第18** |

`【Fact】` 同条第2項により、**営業者はこれらの基準に従い、公衆衛生上必要な措置を定め、
これを遵守しなければなりません。**

`【Fact】` 飲食店営業は「取り扱う食品の特性に応じた取組」でよい営業者に含まれます。
食品衛生法施行令第34条の2第2号は、**飲食店営業**（食品を調理し、または設備を設けて客に飲食させる営業）を
行う者等を第51条第1項第2号の政令で定める営業者として掲げ、
食品衛生法施行規則第66条の3第1号は、飲食店営業（喫茶店営業を含む）を行う者をこれに該当するものとしています。
`【Typical】` これが一般に「**HACCPの考え方を取り入れた衛生管理**」と呼ばれるものです。

`【Fact】` 営業者が具体的に行うべきこととして、食品衛生法施行規則第66条の2第3項は次の4点を定めています。

1. 食品衛生上の危害の発生の防止のため、施設の衛生管理及び食品の取扱い等に関する計画
   （**衛生管理計画**）を作成し、食品を取り扱う者及び関係者に**周知徹底**を図ること
2. 施設設備、機械器具の構造・材質、食品の製造・加工・調理・運搬・貯蔵・販売の工程を考慮し、
   公衆衛生上必要な措置を適切に行うための**手順書**を必要に応じて作成すること
3. **衛生管理の実施状況を記録し、保存すること**
   （保存期間は、取り扱う食品が使用・消費されるまでの期間を踏まえ合理的に設定する）
4. 衛生管理計画及び手順書の**効果を検証し、必要に応じて内容を見直すこと**

`【Fact】` 別表第18は、①危害要因の分析、②重要管理点の決定、③管理基準の設定、
④モニタリング方法の設定、⑤改善措置の設定、⑥検証方法の設定、⑦記録の作成、の7項目を定めています。
`【Typical】` これが一般に「HACCPに沿った衛生管理」と呼ばれるものです。

### 情報の流れとして見た衛生管理記録

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「衛生管理計画で決めたことを、実際に実施したという事実」 |
| **誰が作るか** | ⑧仕込み機能・⑨キッチン機能・⑫清掃・衛生機能（実施した人）／確認は⑦店長機能（食品衛生責任者） |
| **中身** | `【Typical】` 冷蔵庫・冷凍庫の温度／加熱の中心温度／従業員の健康状態／手洗いの実施／清掃の実施／`【Varies】` 店が定めた計画の内容による |
| **誰が使うか** | ⑦店長機能（日々の確認）／代表取締役（営業者）／**保健所**（`【Typical】` 監視指導の際に確認を求められることがある） |
| **どこに保管されるか** | `【Fact】` 記録し、保存する（施行規則第66条の2第3項第3号）。`【Varies】` 紙の記録表、アプリ、自動記録の機器など形態は多様。`【Typical】` 中小飲食企業では紙の記録表で運用している例が多くみられます |
| **次に何に変わるか** | `【Fact】` **検証と見直し**（同項第4号）→ 衛生管理計画の改訂 |
| **頻度** | `日次`／`常時`（`【Varies】` 計画で定めた頻度による） |

### なぜ「記録」なのか（測るだけでは足りない理由）

> `【Inference】` 温度を測るのは**モノの状態を確かめる行為**です。
> 記録に残すのは**確かめたという事実を残す行為**です。
> 施行規則第66条の2第3項第3号が求めているのは後者です。
>
> `【Inference】` 記録があることで可能になるのは次の3つです。
> 1. **第三者が確認できる**（保健所の監視指導、社内の別の人）
> 2. **異常があったときに、いつから異常だったかを遡れる**
>    （`【Example】` 冷蔵庫の温度記録が3日前から高い → その間に保管していた食材の扱いを判断できる）
> 3. `【Fact】` **検証と見直しの材料になる**（同項第4号）

> **食品衛生責任者との関係**
> `【Fact】` 食品衛生責任者は、**上記の措置の遵守のために必要な注意を行うとともに、
> 営業者に対し必要な意見を述べるよう努める**こととされ（施行規則別表第17第1号ホ）、
> **営業者は食品衛生責任者の意見を尊重**しなければなりません（同ニ）。
> `【Inference】` つまり衛生管理記録は、
> **食品衛生責任者が「営業者に意見を述べる」ための材料**でもあります。

> **衛生管理記録が事業の継続に関わる理由**
> `【Fact】` 都道府県知事は、営業者が同法の一定の規定
> （**第51条第2項＝衛生管理の基準に従った措置の遵守義務を含む**）に違反した場合においては、
> 第55条第1項の許可を取り消し、または営業の全部もしくは一部を禁止し、
> もしくは期間を定めて停止することができます（食品衛生法第60条第1項）。
> `【Inference】` したがって衛生管理記録は、
> 「書いておいたほうがよい書類」ではなく、**営業の前提に関わる記録**です。

## 9-14 ★ POSの売上データが翌日の発注と仕込みを決める

飲食業の情報の流れで、**一周して戻ってくる経路**がひとつあります。
これが「昨日の売上が、今日の発注と仕込みを決める」という流れです。

### 循環の全体像

```
 【昨日】
   ⑥オーダー情報 → ⑨会計情報 → POSに記録される
                                    │
                                    ↓
                            売上データが集計される
                            ・売上高
                            ・客数・組数
                            ・客単価
                            ★ メニュー別の出数
                            ・時間帯別の売上
                            ・決済手段別の内訳
                                    │
                                    ↓
                              ⑩日報情報（店長が作る）
                                    │
 ───────────────────────────────────┼───────────────────────
 【今日】                            ↓
                              ②客数見込み情報
                          （前週同曜日の実績・予約・天候と合わせる）
                                    │
                        ┌───────────┴───────────┐
                        ↓                       ↓
                   ③発注情報                ⑤仕込み指示情報
                （何をいくつ買うか）      （何をどれだけ仕込むか）
                        │                       │
                        ↓                       ↓
                   ④納品情報              仕込み品ができる
                        │                       │
                        └───────────┬───────────┘
                                    ↓
                              【今日の営業】
                                    ↓
                             ⑥オーダー情報 → ⑨会計情報 → …（繰り返す）
```

### なぜこの循環が必要なのか

`【Inference】` 飲食業には「注文を受けてから材料を手配する」という選択肢がありません
（`04_end-to-end-process.md` 4-0）。
**注文を受ける前に食材を仕入れ、仕込んでおく**必要があります。
`【Inference】` したがって「どれだけ用意するか」は**過去の実績から推定するしかありません。**
この推定の材料になるのが、POSに蓄積された売上データです。

### 具体的に何が使われるか

| POSから取れる情報 | 何を決めるのに使うか |
|---|---|
| **メニュー別の出数** | `【Typical】` 「牛すじ煮込みは金曜の夜に何食出るか」→ **⑤仕込み指示情報**（仕込み量） |
| 曜日別・時間帯別の客数 | `【Typical】` **②客数見込み情報**／シフトの人数と時間帯 |
| 客単価 | `【Typical】` 売上見込みの計算／メニュー構成の見直し |
| 売上高の推移 | `【Typical】` **③発注情報**（全体の仕入量の目安） |
| 天候・曜日と売上の関係 | `【Typical】` `【Varies】` 過去の実績との突き合わせ |

> `【Example】`（説明用の架空例）モデル企業A店の店長が、金曜の仕込み量を決める場面。
> 「POSで先週の金曜の夜を見ると、牛すじ煮込みの出数は18。
> 　今日は12名の予約が1件あるので、先週より多く出そう。
> 　前日の残りが3人前あるから、追加で15人前を仕込む」
>
> `→ ここで使われている情報は、`
> `　①予約情報（12名）＋ POSの出数データ（先週18）＋ 現物の確認（残り3人前）の3つです。`
> `　どれか1つでも欠けると、仕込み量の判断の精度が落ちます。`

### POSがない場合はどうなるか

`【Typical】` 中小飲食企業では、POSレジを使わず、手書きの伝票と現金のレジで運営している店もあります
（`【Varies】`）。
`【Inference】` この場合、メニュー別の出数は**伝票を数えるか、記憶に頼る**ことになります。
`【Typical】` 実務では、その日の伝票をまとめて集計する、
日報に「出た数」を書き留める、といった形で情報が残されます。
`【Fact】` 本資料は、どちらの方法についても良し悪しの評価を行いません。
**情報の流れとして見たときに、「メニュー別の出数という情報が、どこかで作られ、翌日に使われる」
という構造は共通しています。**

## 9-15 情報が滞るとどうなるか（止まる場所の一覧）

`【Inference】` 情報の流れは、どこかで止まると後工程が動かなくなります。

| 止まる場所 | 止まると何が動かなくなるか | 気づくのはいつか |
|---|---|---|
| ①予約情報が台帳に書かれない | 席が用意されない／仕込みが足りない | **当日、客が来たとき** |
| ①のアレルギー情報が厨房に届かない | 除去すべき食材が入ったまま提供される | `【Inference】` 提供後になり得る |
| ③発注情報が締切に間に合わない | 翌日の食材が届かない | **翌朝** |
| ④納品情報（検品結果）が納品書に残らない | 請求書照合で差異が見つけられない | **月末** |
| ⑤仕込み指示が伝わらない | 仕込みが足りない／余る | **営業中／閉店後** |
| ⑥オーダー情報が通らない | 料理が作られない | **客に呼ばれたとき** |
| 品切れ情報がホールに伝わらない | 出せない注文を受けてしまう | **厨房に通した直後** |
| ⑨会計情報が正しく入力されない | レジ差異が出る／売上データが狂う | **締め作業（当日中）** |
| ⑩日報情報が本部に届かない | 売上の把握が遅れる／資金繰りの判断が遅れる | **本部が気づいたとき** |
| 勤怠の情報が本部に届かない | 給与計算が止まる | **給与計算の締めのとき** |
| A-L 廃棄記録が書かれない | 原価率が上がった原因を追えない | **月次の原価確定のとき** |
| ⑫衛生管理記録が書かれない | `【Fact】` 施行規則第66条の2第3項第3号に定める記録・保存がなされない | `【Typical】` 保健所の監視指導の際など |

> `【Inference】` この表を見ると、**気づくまでの時間に大きな差がある**ことが分かります。
> オーダー情報の誤りは数分で分かりますが、
> 検品結果の記録漏れは月末まで分かりません。
> **気づくのが遅い情報ほど、記録として残す仕組みが必要になります。**

## 9-16 【Example】1つの情報が変わっていく様子を追う

> ### ⚠ 以下はすべて説明用の架空例です
> `【Example】` モデル企業A店で、**「12名の予約」という1つの情報**が
> どのように形を変え、どこに影響したかを追跡します。

```
【予約を受けた日】
 ① 電話で予約が入る
    ホール担当が聞き取る：「◯月◯日の夜、12名、コース、飲み放題つき、
                           1名が甲殻類アレルギー」
    → 予約台帳に記入（①予約情報 が生まれる）
    → 店長に共有

【前日】
 ② 店長が翌日の見込みを立てる
    「予約で20名確定（12名＋4名＋4名）、飛び込みを含めて夜は70名前後」
    → ②客数見込み情報 になる

 ③ 店長が発注を決める
    「12名分のコース食材＋通常営業分」→ ③発注情報 になる
    → 卸へ伝える

【当日・開店前】
 ④ 食材が届く → ④納品情報（納品書＋検品結果）
    レタス1ケース未着 → 「サラダをキャベツに変更」という判断が生まれる

 ⑤ 店長が仕込み量を指示
    「コース用に12名分。牛すじは前日残り3人前なので追加15人前」
    → ⑤仕込み指示情報 になる
    → 調理社員が仕込む → 仕込み品（モノ）になる

 ⑥ 開店準備の情報共有
    「夜の早い時間に12名。甲殻類アレルギーが1名。
     テーブル3卓をつなげる。サラダはキャベツに変更」
    → ①の情報が、席割り・厨房・ホール全員に配られる

【当日・営業中】
 ⑦ 12名が来店。予約台帳と照合して席へ案内
 ⑧ コースの進行に合わせて料理が出る
    甲殻類アレルギーの1名分は、別の料理に差し替えて提供
    → ⑧提供情報 で「こちらがアレルギー対応です」と口頭確認
 ⑨ 途中で「生ビール5杯追加」→ ⑥オーダー情報 が追加で生まれる
 ⑩ 会計 → ⑨会計情報（コース12名分＋飲み放題＋追加ビール＝合計45,000円、現金払い）

【当日・閉店後】
 ⑪ 締め作業で、この45,000円が現金として照合される（A-11）
 ⑫ 日報に記録される → ⑩日報情報
    「夜の客数68名、うち予約20名。売上316,200円」
 ⑬ 残った仕込み品と廃棄を記録 → A-L 廃棄記録

【月末】
 ⑭ 棚卸 → 当月の食材費が確定 → ⑪原価情報
 ⑮ この月のコース予約の件数・売上が、店別損益に反映される

【翌週以降】
 ⑯ 「金曜の夜に12名の予約が入ると、牛すじ煮込みの出数が増える」
    という実績が、次の ②客数見込み情報・⑤仕込み指示情報 の材料になる
```

> **この追跡から読み取れること**
> `【Inference】`
> 1. **1つの予約情報が、少なくとも6種類の情報に変わっている**
>    （②客数見込み → ③発注 → ⑤仕込み指示 → ⑥オーダー → ⑨会計 → ⑩日報）。
> 2. **アレルギー情報だけは、最初から最後まで形を変えずに運ばれている**（①→⑥→⑧）。
>    加工されず、そのまま伝わる必要がある情報です。
> 3. **④納品情報の「欠品」が、⑤仕込み指示と⑥（客への案内）にまで波及している。**
>    情報は一方向に流れるだけでなく、途中で他の情報を書き換えます。
> 4. **最後に数字が確定するのは月末（⑭）**。
>    日々の情報は、月末の原価情報で初めて「いくら残ったか」に変わります。
> 5. **そして⑯で、また最初に戻ります。** これが 9-14 の循環です。
