# 09_information.md — 宿泊業の「情報の流れ」

> 本ファイルは `common/methodology.md` §6 の定義に従い、
> **具体的に「何の情報」かを命名して**整理します。
> 「情報」という抽象語で終わらせず、**販売価格情報・在庫情報・予約情報…**のように名前を付け、
> それぞれについて**誰が作り／誰が使い／どこに保管され／次に何に変わるか**を示します。
>
> ステップ名（A-1〜A-11、B-①〜⑥）は `04_end-to-end-process.md`、
> 機能の番号（①〜⑨）は `03_company-structure.md` 3-2 の定義に従います。
> 機能間の受け渡しの詳細は `05_departments.md` PART 3 にあります。重複する部分は参照で済ませます。

---

## 9-0 【最初に】宿泊業の情報は「1本につながった鎖」である

### 情報は形を変えながら次へ渡っていく

`【Inference】` 宿泊業の情報は、バラバラに存在しているのではありません。
**1つの情報が次の情報の材料になり、その情報がまた次の材料になる**、という鎖になっています。

```
  販売価格情報
      ↓ （価格が決まると、どのチャネルに何室出すかを決められる）
  在庫（残室）情報 ──▶ 各チャネルへの配分情報
      ↓ （配分された在庫が売れると、予約が生まれる）
  予約情報
      ↓ （到着日が近づくと、部屋と食事と清掃に割り当てられる）
  到着前情報（アサイン・特別依頼）
      ↓ （客が到着すると、法定の帳簿ができる）
  チェックイン情報（**宿泊者名簿**）
      ↓ （滞在中の利用が積み上がる）
  滞在中情報
      ↓ （客が出ると、部屋は清掃工程へ）
  清掃状況情報 ──▶ 在庫（残室）情報へ**戻る**
      ↓
  チェックアウト・精算情報
      ↓ （その日の分を締める）
  売上確定情報（ナイトオーディット）
      ↓ （チャネルごとに集計・請求・精算）
  チャネル別入金情報
```

**最後の「清掃状況情報 → 在庫情報」で、鎖は環になります。**
`04_end-to-end-process.md` 4-1 の A-11（次の販売へ）が、これにあたります。

### この鎖のどこかが切れるとどうなるか

`【Inference】` 本ファイルで最も重要な点です。

| 切れる場所 | 何が起きるか |
|---|---|
| **在庫情報が各チャネルで食い違う** | **オーバーブッキング**（9-3） |
| **清掃状況情報がフロントに届かない** | **部屋があるのに客に渡せない**（9-4） |
| **決済区分の情報が予約に付いていない** | **二重請求または取りこぼし** |
| **特別依頼（アレルギー等）が調理に届かない** | **食事を出せない／出してはいけないものを出す** |
| **宿泊者名簿が作られない** | `【Fact】` **法令違反**（罰則あり。9-5） |

## 9-2 各情報の詳細

### 9-2-1 販売価格情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | **日付別・部屋タイプ別・プラン別の販売価格** |
| **誰が作るか** | ① 予約・販売管理機能（`【Example】` Xホテルでは支配人、Y旅館では女将） |
| **何を材料に作るか** | ・今日から先、日付ごとの予約の入り具合（＝在庫情報）<br>・過去の同時期の実績（＝売上確定情報の蓄積）<br>・曜日、連休、地域のイベント<br>・周辺の宿の状況 `【Varies】` |
| **誰が使うか** | ② フロント（問い合わせへの回答、飛び込み客への提示）／OTA・自社サイト・代理店（掲載）／⑦ 営業（法人・団体への提示） |
| **どこに保管されるか** | `【Varies】` PMS、サイトコントローラー、料金表（紙・表計算） |
| **次に何に変わるか** | **各チャネルへの配分情報**（A-2）と一緒に、**各チャネルに表示される「空室数と価格」**になる |
| **頻度** | **日次**（繁忙期）／**週次**（閑散期）`【Varies】` |

**なぜこの情報が要るのか**
`【Inference】` `01_overview.md` 1-1 のとおり**部屋は売れ残ると消える**ため、
「定価を決めたら終わり」にはできません。
**価格そのものが、毎日更新される情報**になります。

### 9-2-2 在庫（残室）情報 ★最も事故が起きやすい情報★

| 項目 | 内容 |
|---|---|
| **何の情報か** | **日付別・部屋タイプ別に、今、あと何室売れるか** |
| **誰が作るか** | 1か所ではありません。**次の4つの機能が同時に増減させています** |
| | ・① 予約・販売管理：配分を変える／団体枠を解放する |
| | ・② フロント：予約を受ける（減る）、キャンセルを受ける（増える） |
| | ・③ 客室清掃：清掃と点検が終わった部屋を「販売可」にする（増える） |
| | ・⑥ 設備管理：故障・修繕で「使用不可」にする（**減る**） |
| **誰が使うか** | ① ②、および**すべての販売チャネル**（OTA・自社サイト・代理店） |
| **どこに保管されるか** | `【Varies】` PMS（正）とサイトコントローラー（各チャネルへの反映） |
| **次に何に変わるか** | **各チャネルに表示される空室数**になり、売れれば**予約情報**に変わる |
| **頻度** | **常時**（予約は24時間入る） |

**なぜこの情報が最も危ないのか**
`【Inference】` **作る人が4つの機能に分かれており、しかも同時に動くから**です。
詳細は 9-3 で扱います。

> `【Example】`（説明用の架空例）Xホテルの3月10日、シングル50室。
> 朝の時点で残り5室 → 10時に清掃完了で1室戻り6室 → 11時20分に設備故障で1室減り5室 →
> 11時30分にOTAで2室売れて3室 → 12時に電話予約で1室売れて2室 →
> 13時にキャンセルが1件出て3室。
> **半日で6回変わっています。** この変化が全チャネルに正しく伝わり続ける必要があります。

### 9-2-3 各チャネルへの配分情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | **どのチャネルに、何室を、いくらで出すか** |
| **誰が作るか** | ① 予約・販売管理機能 |
| **何を材料に作るか** | 全体の販売可能室数、チャネルごとの現在の販売状況、法人契約で確保している枠、団体の仮予約で押さえている枠 |
| **誰が使うか** | OTA（掲載）／自社サイトの予約エンジン／旅行代理店／⑦ 営業（団体・法人への回答） |
| **どこに保管されるか** | `【Varies】` サイトコントローラー、OTAの管理画面（エクストラネット）、PMS |
| **次に何に変わるか** | **各チャネルの画面に表示される空室と価格** → 売れれば**予約情報** |
| **頻度** | **日次**／価格変更時 |

**関連する用語**

- **在庫配分（アロケーション）**
  → どの販売チャネルに何室ずつ割り当てるかを決めること（`02_industry-structure.md` 11-2）。
  → `【Varies】` チャネルごとに枠を切る方法と、全在庫を全チャネルで共有する方法があり、施設により異なります。

- **ブロック（団体枠）**
  → `【Typical】` 旅行代理店や団体客のために「○月○日、20室を押さえておいてほしい」と
    依頼されたとき、その分を一般販売から外して確保しておくこと。
  → `【Typical】` ブロックには「いつまでに確定するか」の期限が設けられ、
    期限までに確定しなければ枠を解放して一般販売に戻します。
  → **なぜ期限を切るのか**：`【Inference】` 押さえたまま期限を過ぎると、
    その部屋は売る機会を失ったまま消えるためです。

- **アロットメント**
  → `【Typical】` 旅行代理店やOTAに対して、あらかじめ一定室数を継続的に割り当てておく取り決めのこと。
  → `【Varies】` 期限（いつまでに使わなければ戻すか）、戻し方、精算の方法は契約により異なります。
  → **なぜするのか**：`【Inference】` 代理店側は「確実に売れる部屋がある」状態で商品を作れ、
    宿側は一定の販売が見込めます。詳細は `15_rules-customs.md` を参照してください。

- **クローズアウト（売止め）**
  → 特定の日付・プラン・チャネルについて、販売を止めること。
  → 実務例：3月10日が満室に近づいたので、安いプランだけを止める。
    OTAの手数料を避けたい日は、そのOTAへの掲載を止める `【Varies】`。
  → **なぜするのか**：`【Inference】` 残り少ない部屋を安いプランで売り切ってしまうと、
    後から来る高い需要を取れなくなるためです。

### 9-2-4 予約情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | **1件ごとの、宿泊日・泊数・人数・部屋タイプ・室数・プラン・氏名・連絡先・特記事項** |
| **誰が作るか** | ② フロント（電話・メール・自社サイト）／**OTA経由はシステムが自動受信し、人が内容を確認する** |
| **誰が使うか** | ① 在庫の反映／② 到着前準備・チェックイン／③ 清掃室数／④⑤ 食数／⑦ 法人・団体の管理／⑧ 請求 |
| **どこに保管されるか** | `【Varies】` PMS。`【Typical】` 中小では**紙の予約台帳と併用**されることもある（`11_systems.md`） |
| **次に何に変わるか** | **在庫情報の減少** → **当日到着リスト**（到着前情報） → **宿泊者名簿**（チェックイン情報） |
| **頻度** | **常時**（OTAは24時間入る）。変更・取消も**常時** |

**予約情報に含まれる項目（`04_end-to-end-process.md` A-3 より）**

| 項目 | なぜ要るか |
|---|---|
| 宿泊日・泊数 | `【Inference】` **どの日の在庫を1つ減らすか**が決まる |
| 人数（大人・子供） | `【Inference】` **食事の数**と**定員**に関わる |
| 部屋タイプ・室数 | `【Inference】` どの在庫を減らすか |
| プラン（素泊まり・朝食付き・2食付き） | `【Inference】` 価格と食事の有無が決まる |
| 氏名・連絡先 | `【Inference】` **チェックイン時の照合**と、変更・遅延の連絡 |
| **決済方法**（事前決済か現地決済か） | `【Inference】` **A-5 の決済区分情報**になる。**これが無いと精算できない** |
| 特記事項（到着予定時刻・アレルギー・駐車場・連泊時の清掃要否） | `【Inference】` 到着前準備で各機能に配る材料になる |

> **初心者がつまずく点：予約情報は「売上」ではありません。**
> `【Typical】` 予約を受けた時点では、まだ売上になりません。
> 売上が確定するのは、原則として宿泊のサービスを提供したとき（A-9 の精算時）です。
> **予約は「将来の売上の見込み」であり、キャンセルされれば消えます。**

### 9-2-5 決済区分情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | **誰が集金するか／いつ集金するか／支払手段は何か** |
| **誰が作るか** | ② フロント（予約時に記録） |
| **誰が使うか** | ② フロント（**チェックアウト時に「この客からいくら受け取るか」を判断する**）／⑧ 経理 |
| **どこに保管されるか** | `【Varies】` PMSの予約記録に紐づけて保管 |
| **次に何に変わるか** | **精算情報**（A-9）→ **チャネル別入金情報**（B-①〜⑥） |
| **頻度** | **予約時**／**到着時**／**請求時** |

**なぜ独立した情報として扱うのか**
`【Inference】` `08_money.md` 8-1 のとおり、**同じ日に同じ内容で泊まる客が、まったく違うお金の流れを持っている**ためです。

> `【Example】`（`04_end-to-end-process.md` A-5 と同じ例）同じ日にチェックアウトする3人。
> - 客あ：OTAで事前決済済み → **フロントでは1円も受け取らない**
> - 客い：直販・現地決済 → **フロントで全額を受け取る**
> - 客う：A社の法人契約 → **フロントでは受け取らず、月末にA社へ請求**
>
> **見た目は同じ「1泊の客」ですが、精算の仕方は3通りです。**
> この3通りを見分ける唯一の手がかりが、決済区分情報です。

### 9-2-6 到着前情報（当日到着リスト・アサイン・特別依頼）

| 項目 | 内容 |
|---|---|
| **何の情報か** | **当日到着リスト**（誰が何時ごろ来るか）／**客室アサイン表**（どの部屋を誰に割り当てるか）／**特記事項**（アレルギー・記念日・高齢の客・団体・車椅子の利用・早着/遅着） |
| **誰が作るか** | ② フロント（`【Varies】` 前日または当日朝） |
| **何を材料に作るか** | 予約情報、清掃状況情報（仕上がりの見込み）、設備の状況（使用不可の部屋） |
| **誰が使うか** | ② フロント（受入）／③ 客室清掃（清掃の室数と**優先順**）／④⑤ 料飲・調理（**食数**と個別対応）／⑥ 設備管理（使用不可の部屋の確認）／⑦ 営業（団体） |
| **どこに保管されるか** | `【Varies】` PMSから出力した到着リスト、アサイン表（紙・画面）、申し送りノート |
| **次に何に変わるか** | ③ へは**清掃指示**、④⑤ へは**食数**、② では**チェックイン情報**の材料になる |
| **頻度** | **日次** |

**アサインとは**

- **アサイン（客室の割り当て）**
  → 予約に対して「実際にどの部屋番号を使うか」を決めること。
  → 実務例：3名の家族連れにはツインにエキストラベッドを入れた部屋を、
    早朝出発の客にはエレベーター近くの部屋を、団体には同じ階の連番の部屋を割り当てる。
  → **なぜするのか**：`【Inference】` 予約の時点では「シングル1室」としか決まっていません。
    部屋によって眺望・広さ・静かさ・エレベーターからの距離が違い、
    また**清掃の進み具合も部屋ごとに違います。**

`【Inference】` アサインは**予約情報と清掃状況情報を突き合わせて作る情報**です。
どちらが欠けても作れません。

### 9-2-7 チェックイン情報（宿泊者名簿・在館情報）

| 項目 | 内容 |
|---|---|
| **何の情報か** | **宿泊者名簿**（法定帳簿）／**在館情報**（今、誰が・何室・何人いるか） |
| **誰が作るか** | ② フロント |
| **誰が使うか** | ② フロント（在館の把握）／⑥ 設備管理・防火管理者（**収容人員の管理**）／④⑤（食事の実数）／**都道府県知事（要求があったとき）** |
| **どこに保管されるか** | `【Fact】` 旅館業の施設、営業者の事務所（旅館業法施行規則第4条の2第2項）。`【Fact】` **作成の日から3年間保存**（同条第1項） |
| **次に何に変わるか** | 在館情報 → **滞在中情報** → **精算情報**。名簿は**保存義務のある記録**として残り続ける |
| **頻度** | **常時**（到着時） |

**この情報だけは、法令が中身を決めています。詳細は 9-5 を参照してください。**

### 9-2-8 滞在中情報（利用明細・要望・不具合）

| 項目 | 内容 |
|---|---|
| **何の情報か** | **客ごとの利用明細**（宿泊料に積み上がっていく飲食・売店・ルームサービス・コインランドリー・駐車場等）／**要望**（アメニティ追加、タオル交換、荷物預かり、タクシー手配）／**不具合**（部屋の設備の故障） |
| **誰が作るか** | ② フロント／④ 料飲／⑤ 調理／⑥ 設備管理 |
| **誰が使うか** | ② フロント（**チェックアウト時の精算**）／⑧ 経理（売上）／⑥ 設備管理（修理） |
| **どこに保管されるか** | `【Varies】` PMSの客ごとの明細、申し送りノート、設備の記録 |
| **次に何に変わるか** | **精算情報**（A-9）／**使用不可の部屋**（在庫情報の減少） |
| **頻度** | **常時** |

**なぜその場で記録するのか**
`【Inference】` 滞在中に発生した利用は、**チェックアウト時にまとめて精算される**のが一般的です。
その場で記録しなければ、**請求漏れ**が起きます。
また、要望は**シフトをまたいで引き継がれる**必要があります（`06_people.md` 6-5）。

### 9-2-9 清掃状況情報 ★宿泊業の心臓部★

| 項目 | 内容 |
|---|---|
| **何の情報か** | **どの部屋が、今、どの状態か**（使用済み／清掃中／清掃済・点検前／**販売可**／使用不可） |
| **誰が作るか** | ③ 客室清掃機能（`【Example】` Xホテルでは**委託先のC清掃**） |
| **誰が使うか** | **② フロント（最重要）**／① 予約・販売管理（当日の販売可能室数）／⑥ 設備管理（不具合のある部屋） |
| **どこに保管されるか** | `【Varies】` 内線電話・無線機（記録なし）／清掃状況表（紙）／PMSの客室ステータス／清掃管理の仕組み |
| **次に何に変わるか** | **「今、渡せる部屋」の一覧**（② が使う） → **売れる在庫**（① が使う） → **在庫情報**へ戻る |
| **頻度** | **日次**（部屋ごとに完了のつど） |

**この情報が届かないとどうなるか → 9-4 で扱います。**

### 9-2-10 チェックアウト・精算情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | **確定した利用明細**（宿泊料＋追加利用＋税）／**受領した金額と支払手段**／**領収書**／（法人の場合）**請求対象データ** |
| **誰が作るか** | ② フロント |
| **誰が使うか** | ⑧ 経理（売上の計上・請求・消込）／③ 客室清掃（**チェックアウト済み＝清掃可能**の連絡） |
| **どこに保管されるか** | `【Varies】` PMS、レジ、領収書の控え |
| **次に何に変わるか** | **売上確定情報**（ナイトオーディット）／**請求書**（法人・代理店）／**清掃対象の部屋** |
| **頻度** | **常時**（出発時） |

**ここに含まれる税**

`04_end-to-end-process.md` A-9 のとおり、精算時には消費税のほか、
`【Fact】` **入湯税**（地方税法第701条以下）、
`【Varies】` **宿泊税**（地方税法第731条の法定外目的税として条例で定める地域のみ）が上乗せされることがあります。
`【Inference】` **これらは宿の売上ではないため、精算情報の中でも分けて記録されます**（`08_money.md` 8-4）。

### 9-2-11 売上確定情報（ナイトオーディットの結果）

| 項目 | 内容 |
|---|---|
| **何の情報か** | **その日の売上の総額と内訳**（宿泊料／料飲／その他／税）／**決済区分別の内訳**（現金・カード・OTA事前決済・請求）／**その日の OCC・ADR・RevPAR**／**日報** |
| **誰が作るか** | ② フロント（`【Example】` Xホテルでは夜勤者）／⑧ 経理 |
| **誰が使うか** | **① 予約・販売管理（翌日以降の価格判断＝A-1 の材料）**／⑧ 経理（月次の請求・消込・試算表）／支配人・社長 |
| **どこに保管されるか** | `【Varies】` PMS、日計表（紙・表計算）、会計ソフト |
| **次に何に変わるか** | **月次の売上集計** → **請求書**（法人・代理店） → **チャネル別入金情報** |
| **頻度** | **日次** |

`【Inference】` **この情報が、経理の入口であると同時に、翌日の価格の材料でもある**点が宿泊業の特徴です
（`08_money.md` 8-2-4）。

### 9-2-12 チャネル別入金情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | **チャネルごとに、いつ・いくら入金されたか**／**OTA・代理店の精算明細**／**未入金の一覧** |
| **誰が作るか** | ⑧ 経理・財務機能（入金は相手方から。明細はOTA・代理店から） |
| **誰が使うか** | ⑧ 経理（消込・督促）／社長（資金繰り） |
| **どこに保管されるか** | `【Varies】` 会計ソフト、通帳・入出金明細、OTAの管理画面から取得した精算明細 |
| **次に何に変わるか** | **消込済みの売掛金** → **月次の試算表** → **年次の決算** |
| **頻度** | **月次** `【Varies】` |

**なぜ「チャネル別」と名付けるのか**
`【Inference】` `08_money.md` 8-1 のとおり、**入金の形がチャネルごとにまったく違う**からです。
「入金情報」と一言でまとめると、**現金のレジ締め・カードの消込・OTAの精算明細の突合・
法人の請求と督促という4種類の別作業が同じものに見えてしまいます。**

## 9-3 在庫情報が各チャネルで食い違うと、オーバーブッキングになる

### 9-3-1 オーバーブッキングとは

- **オーバーブッキング（二重予約）**
  → 実際に用意できる部屋数を超えて予約を受けてしまっている状態のこと。
  → 実務例：シングル50室しかないのに、3月10日のシングルの予約が52件入っている。
  → **なぜ重大か**：`【Inference】` 客は「今夜寝る場所」を確保したつもりで来ています。
    部屋がないことは、**他の商品の欠品とは意味が違います。**

### 9-3-2 なぜ起きるのか — 情報の構造から説明する

`【Inference】` 原因は**情報の構造そのもの**にあります。

```
  【1つの在庫】3月10日のシングル50室
        │
        ├───────┬───────┬───────┬───────┐
        ▼       ▼       ▼       ▼       ▼
     自社サイト  OTA①   OTA②   OTA③   代理店   ← **5か所に同時に並んでいる**
        │       │       │       │       │
        └───────┴───────┴───────┴───────┘
                     ▲
        **どこか1か所で売れたら、残り4か所の在庫を即座に減らさなければならない**
```

`【Inference】` **この「即座に」が守られない瞬間に、オーバーブッキングが生まれます。**

`【Typical】` 主な発生原因（`04_end-to-end-process.md` 4-3 ② と同じ）

| 原因 | 情報としては何が起きているか |
|---|---|
| **在庫反映の遅れ** | 1か所で売れた情報が、他のチャネルに届くまでに時間がかかる |
| **手入力の誤り** | 電話予約の入力漏れ・日付の入力誤り → **在庫情報が実態とずれる** |
| **客室の使用不能** | 設備故障・水漏れ・破損で急に部屋が使えなくなる → **売れる部屋数が減ったのに、チャネルの表示が減らない** |
| **滞在延長** | 連泊中の客が急に延泊を申し出る → **空くはずだった部屋が空かない** |
| **団体枠の管理ミス** | ブロックを解放し忘れる／**二重に解放する** |

### 9-3-3 だからサイトコントローラーという仕組みがある

- **サイトコントローラー**
  → 複数の販売チャネル（自社サイト・OTA各社・代理店）の**在庫と料金を一括で同期させる仕組み**のこと。
  → 実務例：OTA①で1室売れると、その情報を受けて自社サイト・OTA②・OTA③の在庫も自動で1室減らす。
    価格を変えるときも、1か所で変えれば全チャネルに反映される。
  → **なぜ必要か**：`【Inference】` 5か所の画面を人が1つずつ更新していては、
    その作業の間に別のチャネルで売れてしまうためです。

`【Inference】` つまりサイトコントローラーは、
**「在庫情報を1つに保つ」ためだけに存在する仕組み**です。
システムとしての説明は `11_systems.md` を参照してください。

> **本資料は、この仕組みが何のための道具かを説明するものであり、
> 導入の是非や良し悪しを述べるものではありません**（`common/methodology.md` §0）。

### 9-3-4 それでも食い違ったときに動く情報

`【Typical】` オーバーブッキングが判明したときに流れる情報は次のとおりです。

```
  ② フロント（または ① ）が気づく
        │  「3月10日のシングルが51件。50室しかない」
        ▼
  ③ 客室清掃・⑥ 設備管理へ  ：「使える部屋は本当に50室か」（使用不可の部屋の確認）
        │
        ▼
  支配人が判断（`06_people.md` 6-3-2 の RACI 表：承認＝支配人）
        │
        ├─▶ 別の客室タイプへの振替 → ② から客へ連絡
        └─▶ 他施設への振替（送客）とその費用の負担 `【Varies】` → 他施設・OTA・代理店へ連絡
```

`【Varies】` 実際の対応方法・費用負担は施設・契約により異なります。

## 9-4 「清掃が終わった部屋」の情報がフロントに届かないと、部屋を渡せない

### 9-4-1 なぜそうなるのか

`【Inference】` 理由は単純です。**フロントは客室の中を見ていません。**

フロントカウンターから4階の406号室が仕上がったかどうかは、物理的に見えません。
**③ 客室清掃からの報告だけが、唯一の情報源です。**

> `【Example】`（説明用の架空例。`05_departments.md` E-③-6 と同じ場面）Xホテル・14時20分
>
> | 時刻 | 起きたこと | 結果 |
> |---|---|---|
> | 14:20 | 清掃会社が406号室を仕上げたが、まとめて15時に報告する運用だった | フロントは406を「清掃中」と認識 |
> | 14:25 | 早着の客が到着。「部屋に入れますか」 | フロントは**渡せる部屋が無いと判断し、ロビーで待ってもらう** |
> | 15:00 | 清掃会社から一括報告。406を含む12室が「済」 | 客は35分間ロビーで待った |
>
> **部屋は14時20分の時点で存在していました。情報だけが無かったのです。**

### 9-4-2 逆方向も同じだけ重要

`【Inference】` ③ 客室清掃は、**客がいつ出たかを知りません。**
「10時にチェックアウト予定」と分かっていても、実際に出たのは9時20分かもしれず、
11時30分まで部屋にいるかもしれません。

`【Inference】` ② からの「今、この部屋が空いた」が遅れれば、**清掃の開始そのものが遅れます。**
そして清掃が遅れた分は、そのまま「午後に渡せる部屋が減る」に変わります。

### 9-4-3 この情報は ① にも効いている

`【Inference】` さらにもう1段あります。

| 客室の状態 | ① 予約・販売管理から見た扱い |
|---|---|
| チェックアウト済・清掃前 | **まだ売れない** |
| 清掃中 | **まだ売れない** |
| 清掃済・点検前 | **まだ売れない** |
| **清掃済・販売可** | **売れる** |
| 使用不可（故障・修繕） | **売れない** |

`【Inference】` つまり清掃状況情報は、
**② が客に部屋を渡せるかどうかだけでなく、① が当日の飛び込み客（ウォークイン）を
受けられるかどうかも決めています。**

### 9-4-4 伝え方は違っても、中身は同じ

`【Varies】` 伝え方は施設により異なります（`05_departments.md` PART 3 3-2-4）。

| 伝え方 | どういうものか | 記録は残るか |
|---|---|---|
| 内線電話・無線機 | 仕上がるたびに ② へ口頭で伝える | `【Inference】` 残らない |
| 清掃状況表への記入 | 紙の表に部屋番号と状態を書く | 残る |
| PMS の客室ステータス更新 | 清掃側が直接システムの状態を変える | 残る |
| 清掃管理の仕組み `【Varies】` | 清掃側の端末から状態を送る | 残る |
| 一括報告 | 一定時刻にまとめて伝える | `【Varies】` |

> `【Inference】` **どの伝え方であっても、受け渡される中身は同じ**です。
> ・**どの部屋が、今、販売可になったか**
> ・**まだ終わっていない部屋はどれで、いつ終わる見込みか**
> ・**売ってはいけない部屋はどれか**

**この連携の詳細は `05_departments.md` PART 3（特に 3-2）を参照してください。**

### 9-4-5 外部委託の場合、この情報は社外を通る

`【Example】` Xホテルは客室清掃を外部委託しています。
`【Inference】` したがって清掃状況情報は、**社外（C清掃）から社内（② フロント）へ渡る情報**です。

| 論点 | 自社で清掃（Y旅館） | 外部委託（Xホテル） |
|---|---|---|
| 情報の経路 | 清掃パート → 女将（1段） | 清掃スタッフ → **C清掃の責任者** → 支配人／② フロント（2段） |
| 報告の運用 | その場で口頭 | **契約で決まる** `【Varies】` |
| 点検（インスペクション）を誰が行うか | 女将 | `【Varies】` 支配人または委託先の責任者 |

## 9-5 宿泊者名簿は法令上の義務

> `common/methodology.md` の鉄則に従い、**条文の語をそのまま引用します。要約・言い換えはしません。**

### 9-5-1 備付け・記載・提出の義務

`【Fact】` **旅館業法第6条第1項**
> 「営業者は、厚生労働省令で定めるところにより、
> **旅館業の施設その他の厚生労働省令で定める場所に宿泊者名簿を備え、
> これに宿泊者の氏名、住所、連絡先その他の厚生労働省令で定める事項を記載し、
> 都道府県知事の要求があつたときは、これを提出しなければならない。**」

`【Fact】` **旅館業法第6条第2項**（宿泊者の側の義務）
> 宿泊者は、営業者から請求があつたときは、前項に規定する事項を告げなければならない。

`【Fact】` **旅館業法第12条**
> 第6条第2項の規定に違反して**偽つて告げた者**は、**拘留又は科料**に処する。

`【Fact】` **旅館業法第11条第1号**
> 第5条第1項又は**第6条第1項の規定に違反した者**は、**五十万円以下の罰金**に処する。

### 9-5-2 省令が定める詳細（旅館業法施行規則第4条の2）

`【Fact】`

| 項目 | 内容 | 根拠 |
|---|---|---|
| **作成の要件** | **正確な記載を確保するための措置を講じた上で作成すること** | 第1項 |
| **保存期間** | **作成の日から3年間** | 第1項 |
| **備える場所** | ① 旅館業の施設、② 営業者の事務所 | 第2項 |
| **記載事項（法律）** | 宿泊者の**氏名・住所・連絡先** | 法第6条第1項 |
| **記載事項（省令・追加）** | 宿泊者が**日本国内に住所を有しない外国人**であるときは、**その国籍及び旅券番号** | 第3項第1号 |
| **記載事項（省令・追加）** | その他**都道府県知事が必要と認める事項** | 第3項第2号 |

### 9-5-3 設備の側からも求められている

`【Fact】` **旅館業法施行令第1条第1項第2号**は、旅館・ホテル営業の構造設備の基準として、
**宿泊しようとする者との面接に適する玄関帳場その他当該者の確認を適切に行うための設備**として
厚生労働省令で定める基準に適合するものを有することを求めています。

`【Fact】` その厚生労働省令である**旅館業法施行規則第4条の3第2号**は、
**宿泊者名簿の正確な記載、宿泊者との間の客室の鍵の適切な受渡し及び
宿泊者以外の出入りの状況の確認を可能とする設備を備えていること**を定めています。

`【Inference】` つまり法令は、
**「名簿を正しく書けること」と「誰が出入りしているか分かること」を設備面から担保しようとしています。**
フロントでの本人確認は、この要請に応える実務です。

### 9-5-4 なぜこの情報が法定なのか

`【Inference】` 宿泊者名簿は、
**感染症が発生したときに誰がその施設に泊まっていたかを追跡できるようにするため**、
また**事件・事故が起きたときの手がかりとするため**の仕組みです。
`【Fact】` 旅館業法第1条が定める目的（公衆衛生及び国民生活の向上に寄与すること）と対応しています。

> **初心者がつまずく点：「面倒な書類」ではなく「法定帳簿」です。**
> 宿泊者名簿は、宿が自主的に作っている顧客リストではありません。
> **法律で記載事項・保存期間・提出義務が決まっている帳簿**であり、不備には罰則があります。

### 9-5-5 民泊（住宅宿泊事業）にも名簿の義務がある

`【Fact】` 住宅宿泊事業法第8条は、**宿泊者名簿の備付け等**について定めています。

> **ただし、根拠となる法律が違います。**
> `common/methodology.md` の鉄則のとおり、
> **旅館業法第6条と住宅宿泊事業法第8条を一文にまとめてはいけません。**
> 適用される事業も、他に課される義務も違います（`03_company-structure.md` 3-4 の比較表、`15_rules-customs.md`）。

### 9-5-6 個人情報としての側面 `【Varies】`

`【Varies】` 宿泊者名簿には氏名・住所・連絡先が記載されるため、
個人情報の取扱いに関する法令の適用も問題になりますが、
**本資料では個人情報保護法の条文を確認していないため、具体的な要件は記載しません。**
`05_departments.md` E-⑨-8（教育訓練）に、個人情報の取扱いが教育項目として挙げられています。

## 9-6 情報が形を変えていく様子（1本の線で追う）

> `【Example】`（説明用の架空例。`04_end-to-end-process.md` 4-4 ケース1と同じ場面）
> A商事のSさんの1泊を、**情報の側から**追い直します。

| 時点 | 情報の名前 | 誰が作ったか | どこに保管されたか | 次に何に変わったか |
|---|---|---|---|---|
| 2月20日 | **販売価格情報**（3月10日のシングルの価格） | ① 支配人 | PMS／サイトコントローラー | **各チャネルへの配分情報**へ |

### 情報の名前（後続ファイルはこの名称を使うこと）

### 押さえるべき7点

1. **宿泊業の情報は1本の鎖であり、最後に環を閉じる。**
   清掃状況情報が在庫情報に戻ることで、A-11 から A-1 へつながる。
2. **在庫情報だけは「作る人」が4つの機能に分かれている**（①②③⑥）。
   だから最も事故が起きやすく、**食い違えばオーバーブッキングになる。**
3. **サイトコントローラーは「在庫情報を1つに保つ」ためだけの仕組み。**
4. **清掃状況情報が ② に届くまで、その部屋は「無い」のと同じ。**
   フロントは客室の中を見ていないため、③ からの報告だけが唯一の情報源。
   逆に ② → ③ の「今、この部屋が空いた」が遅れれば、清掃の開始が遅れる。
5. **決済区分情報が無ければ、チェックアウト時に「いくら受け取るか」が判断できない。**
   同じ日に同じ内容で泊まった客が、3通りの精算になる。
6. **宿泊者名簿は法定帳簿。**
   旅館業法第6条第1項（備付け・記載・提出）、施行規則第4条の2（**作成の日から3年間保存**、
   備える場所、**日本国内に住所を有しない外国人は国籍及び旅券番号**）、
   第6条第2項（宿泊者の告知義務）、第12条（偽って告げた者は拘留又は科料）、
   第11条第1号（営業者の違反は50万円以下の罰金）。
   **民泊の名簿は住宅宿泊事業法第8条であり、別の法律。一文にまとめてはいけない。**
7. **売上確定情報（ナイトオーディット）の出口は、経理だけでなく翌日の価格判断にも向かう。**
