# 09_information.md — 情報の流れ（情報通信業）

**対象**：日本国内の中小情報通信業（受託開発を主業とするソフトウェア会社）
**読み手**：情報通信業をまったく知らない人
**前提**：`03_company-structure.md` で設定した**Xシステム株式会社**（従業員48名・技術者40名・年商4億5,000万円）【Example】
**最終更新**：2026-09-20

> このファイルは、`common/methodology.md` §6 の「4つの流れ」のうち**情報**を扱います。
> §6 は「『情報』という抽象語で終わらせない。**具体的に何の情報かを命名する**」と定めています。
> 本ファイルでは、**16種類の情報に名前を付け**、それぞれが「どこで生まれ、誰から誰へ渡り、何を決めるために使われるか」を追います。

---

## 9-0. この業界で「情報」が特別に重い理由

### 物理的なモノがないので、情報だけが仕事の実体

07で見たとおり、この業界には材料も在庫も出荷もありません。
**動くのは、成果物（＝情報の集まり）と作業時間だけ**です。

```
  製造業      ：材料が動く → 現物を見れば進み具合が分かる
  情報通信業  ：情報しか動かない → 記録しなければ、何も分からない
```

> **★この違いが決定的です。**
> 製造業なら、仕掛品の山を見れば「どのくらい進んだか」がおおよそ分かります。
> **ソフトウェア開発では、作りかけのものは目に見えません。**
> 「90%できています」という報告が本当かどうかを、外から確かめる方法がありません。
> **だから、記録の有無がそのまま経営の見通しの有無になります。**

### この章を貫く3つの原則

| 原則 | 内容 | どこで詳述するか |
|---|---|---|
| **① 工数の実績が記録されないと、赤字かどうかが分からない** | 契約金額は固定。動くのは実績工数だけ。記録がなければ引き算ができない | 9-3 |
| **② 仕様変更は記録しないと、費用を回収できない** | 口頭で引き受けた変更は、追加請求の根拠にならない | 9-4 |
| **③ 顧客から預かった情報は、自社のものではない** | 秘密保持契約と、個人情報の取り扱いの取り決めに縛られる | 9-5 |

## 9-1. 情報の全体マップ——16の情報に名前を付ける

### (1) 一本の流れで見る

```
 【受注するまで】
   ① 引合い情報 ──▶ ② 要件情報 ──▶ ③ 工数見積情報 ──▶ ④ 提案・見積情報 ──▶ ⑤ 契約情報

 【作るまで】
   ⑥ 要件定義書 ──▶ ⑦ 設計書 ──▶ ⑧ ソースコード ──▶ ⑨ テスト結果情報
        │              │              │
        └──────────────┴──────────────┴──▶ ⑩ 作業実績情報（工数）
                                              │
                                              ▼
                                         ⑪ 進捗情報
                                              │
                        （途中で発生）──▶ ⑫ 仕様変更情報

 【お金になるまで】
   ⑬ 検収情報 ──▶ ⑭ 請求情報 ──▶ ⑮ 入金情報

 【納めたあと】
   ⑯ 障害情報 ──▶ ⑰ 対応記録
```

### (2) 一覧表

| # | 情報の名前 | どこで生まれるか | 誰から誰へ | 何を決めるために使うか |
|---|---|---|---|---|
| ① | **引合い情報** | 顧客・仲介事業者からの連絡 | 営業 → PM・要員管理 | **提案に進むかどうか** |
| ② | **要件情報** | 顧客へのヒアリング | SE・営業 → PM | **何を作るか／何人月かかるか** |
| ③ | **工数見積情報** | 機能一覧からの積み上げ | PM → 社長 | **いくらで出すか** |
| ④ | **提案・見積情報** | 見積書・提案書の作成 | 営業 → 顧客 | **顧客が発注するかどうか** |
| ⑤ | **契約情報** | 契約書・注文書・注文請書 | 社長・総務 → PM・経理 | **完成責任の有無／請求できる時期** |
| ⑥ | **要件定義書** | 顧客との共同作業 | SE → 顧客・開発 | **設計と検収の基準** |
| ⑦ | **設計書** | 外部設計・内部設計 | SE → PG・顧客 | **何をどう作るか** |
| ⑧ | **ソースコード** | 実装 | PG → テスト・顧客 | **動くシステムの実体** |
| ⑨ | **テスト結果情報** | テストの実施 | テスト担当 → PM・顧客 | **納品してよいかどうか** |
| ⑩ | **作業実績情報（工数）** | 技術者本人の入力 | 開発 → PM → 経理 | **★赤字かどうか** |
| ⑪ | **進捗情報** | WBSと実績の突き合わせ | PM → 社長・顧客 | **間に合うかどうか／人を足すか** |
| ⑫ | **仕様変更情報** | 顧客からの追加要望 | 顧客 → PM → 営業 → 顧客 | **★追加費用を請求できるかどうか** |
| ⑬ | **検収情報** | 顧客の検査 | 顧客 → PM → 経理 | **★請求できるかどうか** |
| ⑭ | **請求情報** | 請求書の作成 | 経理 → 顧客 | **いくら受け取るか** |
| ⑮ | **入金情報** | 銀行口座の確認 | 銀行 → 経理 | **売掛金が回収できたか** |
| ⑯ | **障害情報** | 稼働中のシステムの異常 | 顧客・監視の仕組み → 保守 | **何が起きたか／いつ直るか** |
| ⑰ | **対応記録** | 障害・問い合わせへの対応 | 保守 → 顧客・開発 | **同じことが起きたときの手がかり** |

## 9-2. 受注までの情報——①〜⑤

### ① 引合い情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「こういう仕事の話がある」という最初の情報 |
| **具体的に何が入っているか** | 案件名、顧客名、案件の概要、希望時期、おおよその規模（人数・期間・金額感）、求める技術、担当者 |
| **どこから来るか** | 取引先からの連絡／既存案件の担当者からの相談／**SES仲介事業者からの案件情報**／社長への直接の相談 |
| **誰が受け取るか** | 営業機能（営業担当・社長） |
| **どこに記録するか** | **案件管理表（引合い台帳）** |
| **誰に渡すか** | PM（技術的に対応できるか）、要員管理機能（人を出せるか） |
| **何を決めるために使うか** | **提案に進むかどうか**（受けられない案件を早めに断ることも含む） |
| **記録しないと何が困るか** | 【Typical】どの案件がいくらで、いつ決まるかが分からなくなる。**⑨受注見込み（売上予測）が作れない** |
| **頻度** | 案件発生時 |

> **★SESの引合い情報は、受託開発と形が違います**
> 【Typical】受託開発の引合いは「こういうシステムを作りたい」ですが、
> SESの引合いは「**◯月から、この技術ができる人を2名**」という**人の要求**です（04の4-3）。
> そのため、引合い情報の中身も変わります。
>
> | 受託開発の引合い情報 | SESの引合い情報 |
> |---|---|
> | 作りたいシステムの概要 | **必要な人数** |
> | 希望する納期 | **開始時期と期間** |
> | 予算感 | **月額単価の目安** |
> | 必要な機能の範囲 | **求めるスキル・経験年数** |
> | — | **常駐場所（通える範囲か）** |

### ② 要件情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「何を作るのか／何をするのか」を顧客から聞き取った内容 |
| **具体的に何が入っているか** | 現在の業務のやり方、困っていること、作りたい機能、他システムとの連携の要否、データ移行の要否、稼働希望日、顧客側の作業分担 |
| **どこから来るか** | 顧客へのヒアリング（訪問・オンライン会議）、RFP（提案依頼書）【Varies】 |
| **誰が集めるか** | SE・PM（営業が同行） |
| **どこに記録するか** | **ヒアリングシート／議事録**、**機能一覧（案）** |
| **誰に渡すか** | PM（③工数見積のため） |
| **何を決めるために使うか** | **何を作るか／何人月かかるか** |
| **記録しないと何が困るか** | 【Typical】**「言った・言わない」になります。**<br>後から「その機能は話したはずだ」と言われても、記録がなければ反論できません |
| **頻度** | 案件発生時 |

> **★ここで確認しきれなかった項目が、後で費用になります**
> 04の②が述べているとおり、「受注管理システムを作りたい」という一言の中には、
> 画面が10本なのか50本なのか、他システムと連携するのかしないのか、
> 過去データを移すのか移さないのか、が含まれています。
> **ここで確認しきれなかった項目は、後から「追加作業」として出てきます。**

### ③ 工数見積情報★

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「何に何人日かかるか」を積み上げた内訳 |
| **具体的に何が入っているか** | 機能ごとの本数（画面・帳票・バッチ・連携・データ移行）、1本あたりの目安工数、工程ごとの工数、役割別の単価、リスク分（バッファ） |
| **どこから来るか** | ②要件情報（機能一覧）＋**過去の類似案件の実績工数**（⑩から） |
| **誰が作るか** | 見積・提案機能（PM4名＋営業部長、最終判断は社長）【Example】 |
| **どこに記録するか** | **工数内訳表（見積内訳書）**、機能一覧、体制表 |
| **誰に渡すか** | 社長（決裁）→ 営業（顧客へ） |
| **何を決めるために使うか** | **いくらで出すか。その金額で粗利が確保できるか** |
| **記録しないと何が困るか** | 【Typical】**なぜその金額になったかを説明できません。**<br>顧客から「なぜこの金額か」と聞かれたときに答えられず、値引き交渉で根拠を失います |
| **頻度** | 案件発生時 |

> **★この情報が、後の「赤字かどうか」の基準になります**
> 05の5-15が示すとおり、請負の利益は
> **「契約金額 −（実績工数 × 原価単価）− 外注費」**で決まります。
> この式の「契約金額」を決めるのが工数見積情報です。
> **見積の時点で、許される原価の上限が確定してしまいます。**

**【Example】工数見積情報の中身**（04の4-5より。説明用の架空例）
| 項目 | 工数（人月） | 単価（万円） | 金額（万円） |
|---|---:|---:|---:|
| 要件定義（SE） | 1.5 | 85 | 127.5 |
| 外部設計（SE） | 2.0 | 85 | 170.0 |
| 内部設計（SE） | 1.5 | 85 | 127.5 |
| 開発（PG） | 6.0 | 60 | 360.0 |
| テスト（SE・PG） | 3.0 | 70 | 210.0 |
| データ移行（SE） | 1.0 | 85 | 85.0 |
| プロジェクト管理（PM） | 1.4 | 110 | 154.0 |
| **小計** | **16.4** | | **1,234.0** |

### ④ 提案・見積情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 顧客に提示する、体制・進め方・スケジュール・金額 |
| **具体的に何が入っているか** | **見積書**（金額と内訳）、**提案書**（体制・進め方・実績）、**前提条件書**（含まない範囲の線引き） |
| **どこから来るか** | ③工数見積情報 |
| **誰が作るか** | 見積・提案機能（PM）＋営業機能 |
| **誰に渡すか** | **顧客** |
| **何を決めるために使うか** | **顧客が発注するかどうか** |
| **記録しないと何が困るか** | **前提条件書がないと、「含まれていると思った」作業を無償でやることになります** |
| **頻度** | 案件発生時 |

> **★前提条件書は「何を含まないか」を書く書類です**
> 【Typical】見積書には「やること」を書きますが、前提条件書には「**やらないこと**」を書きます。
> - テストデータは顧客が用意する
> - 開発環境・検証環境は顧客が用意する
> - 操作マニュアルは含まない
> - 既存システムの仕様書は現行のものが提供される前提
>
> これを書いていないと、後から言われた作業を断る根拠がありません（05の②-6）。

### ⑤ 契約情報★

| 項目 | 内容 |
|---|---|
| **何の情報か** | 合意した条件のすべて |
| **具体的に何が入っているか** | **契約類型（請負か準委任か）**、金額、納期、**納入物の範囲**、**検収の期間と方法**、支払条件（締め日・支払日）、**契約不適合責任の期間**、**再委託の可否**、**知的財産権の帰属**、秘密保持、変更管理の手続き |
| **どこに記録するか** | **基本契約書／個別契約書／注文書・注文請書**、契約管理台帳 |
| **誰が確認するか** | 社長（【Varies】顧問弁護士に相談） |
| **誰に渡すか** | PM（何を守るべきか）、経理（いつ請求できるか）、要員管理（再委託できるか） |
| **何を決めるために使うか** | **完成責任があるか／いつ請求できるか／協力会社を使えるか** |
| **記録しないと何が困るか** | 04の⑥が述べるとおり、**作業を始めても請求できません** |
| **頻度** | 受注時 |

> **★契約情報は、社内の3つの機能に別々のことを伝えます**
>
> | 誰に | 何を伝えるか |
> |---|---|
> | **PM** | 納入物は何か／検収期間は何日か／変更はどの手続きで行うか |
> | **経理** | いつ請求できるか（検収後か、毎月か）／締め日・支払日はいつか |
> | **要員管理** | 協力会社を使えるか（再委託の可否）／秘密情報を協力会社に見せてよいか |

## 9-3. 作るときの情報——⑥〜⑪

### ⑥ 要件定義書

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「何を作るか」を文書で確定したもの |
| **誰が作るか** | SE（顧客と共同で作る） |
| **誰が承認するか** | **顧客** |
| **誰に渡すか** | 開発機能（設計の入力）、テスト機能（テストの基準） |
| **何を決めるために使うか** | **設計の出発点であり、検収の基準** |
| **記録しないと何が困るか** | **検収のときに「合格」の基準がなくなります**。<br>04の4-5の例では、稼働2か月後に「要件定義書の記述と設計書の記述が食い違っていた」ことが判明し、無償修正が発生しました |
| **頻度** | 案件発生時 |

> **★なぜ要件定義を準委任で契約することが多いのか**
> 【Typical】要件定義は「何を作るか」を決める工程です。
> 決まっていないものの完成を約束することはできないため、
> **「完成」を約束する請負にはなじみません**（05の⑪-3）。
> そのため要件定義は準委任とし、要件が固まってから開発工程を請負で契約し直す、
> という**多段階契約**の形が標準になっています（02の11-3）。

### ⑦ 設計書

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「どう作るか」を決めた文書 |
| **2種類ある** | **外部設計書**（利用者から見える部分：画面・帳票・連携）／**内部設計書**（内部構造・データベース） |
| **誰が作るか** | SE |
| **誰が承認するか** | 外部設計書は**顧客**／内部設計書は【Typical】社内のレビューのみ |
| **誰に渡すか** | PG（実装の指示書）、テスト機能（テストケースの元） |
| **何を決めるために使うか** | **PGが何を作ればよいか** |
| **記録しないと何が困るか** | 【Typical】PGが判断で作ることになり、**要件と違うものができます**。<br>また、後で直す人が中身を追えません |
| **頻度** | 案件発生時 |

> **★設計書には「版」があります**（07の7-1(5)）
> 仕様変更のたびに書き換わるため、**どの版で顧客が承認したか**が重要になります。

### ⑧ ソースコード

| 項目 | 内容 |
|---|---|
| **何の情報か** | プログラムの本体（人が読める形の指示の文章） |
| **誰が作るか** | PG（SE がレビューする） |
| **どこに記録するか** | **ソースコード管理の仕組み**（誰が・いつ・何を変えたかの履歴が残る） |
| **誰に渡すか** | テスト機能、【Varies】顧客（契約で納入物に含まれる場合） |
| **何を決めるために使うか** | **動くシステムの実体** |
| **記録しないと何が困るか** | 【Typical】複数人が同時に触ると、**お互いの修正を上書きしてしまいます**。<br>また、障害のとき「どの版で起きたか」を特定できません |
| **頻度** | 日次（作業のたびに記録される） |

### ⑨ テスト結果情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「ちゃんと動くことを確かめた」記録 |
| **具体的に何が入っているか** | **テスト仕様書（テストケース一覧）**：どんな操作をしたらどうなるはずか<br>**テスト結果記録**：実施した結果（合格／不合格）<br>**不具合票／不具合一覧**：見つかった問題の内容・原因・対応・状態<br>**既知の問題一覧**：残したまま納品する問題 |
| **誰が作るか** | SE・テスト担当 |
| **誰に渡すか** | PM（リリース判定のため）、顧客（検収のとき） |
| **何を決めるために使うか** | **納品してよいかどうか**（リリース判定） |
| **記録しないと何が困るか** | 「確かめた」ことを顧客に示せません。<br>また、**どこまで確かめたかが分からない**ため、抜けに気づけません |
| **頻度** | 案件発生時（テスト工程） |

### ⑩ 作業実績情報（工数）★★

> **この情報が、この業界でもっとも重要な社内情報です。**

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「誰が・どの案件に・どの工程で・何時間使ったか」 |
| **誰が記録するか** | **技術者本人**（SE・PG・テスト担当・保守担当） |
| **どこに記録するか** | 工数入力の仕組み／表計算ソフト【Varies】 |
| **誰が使うか** | **PM**（③-4 見積工数との差を見る）→ **経理**（⑩-10 案件別損益を出す）→ **見積・提案機能**（次の見積の根拠にする） |
| **何を決めるために使うか** | **★いま黒字か赤字か／人を足すか／次の見積をいくらにするか** |
| **頻度** | **日次**（入力）／月次（集計） |

#### ★工数の実績が記録されないと、赤字かどうかが分からない

```
  請負の利益 ＝ 契約金額 −（実績工数 × 原価単価）− 外注費 − その他の原価
                   ↑固定          ↑これが記録されないと計算できない
```

| 情報 | どこにあるか | 持っている機能 |
|---|---|---|
| **契約金額**（固定された売上） | 契約書 | ⑪契約・法務 → ⑩経理・財務 |
| **実績工数**（動く原価の「量」） | **技術者本人の入力** | ④開発 → ③PM |
| **原価単価**（工数を金額に変える係数） | 給与・人件費のデータ | ⑨人事・採用 → ⑩経理・財務 |

**この3つを掛け合わせないと、「いま黒字か赤字か」が出ません。**
PMは工数を持っていますが、各人の原価単価（給与）は通常見ていません。
経理は原価単価を持っていますが、現場の進捗は見ていません。
**だから月次で突き合わせます**（05の③-4と⑩-10）。

> **★記録がないと、具体的に何が起きるか**
>
> | 場面 | 記録があるとき | 記録がないとき |
> |---|---|---|
> | 案件の途中 | 「このままいくと15.5人月。0.9人月超過」と予測できる | **終わるまで分からない** |
> | 遅れが出たとき | 人を足すか、顧客と交渉するかを判断できる | **気づいたときには手遅れ** |
> | 案件の終了後 | 「この顧客は平均15%超過する」と分かる | **同じ間違いを次も繰り返す** |
> | 顧客との交渉 | 「顧客の回答待ちで0.6人月かかった」と示せる | **交渉の根拠がない** |
>
> 【Example】04の4-5の案件では、11月に「進捗が10日分遅れている」ことが工数の記録から判明し、
> 12月に協力会社を1名追加投入する判断ができました。**記録がなければ、1月の納期直前に気づくことになります。**

> **★なぜ入力されにくいのか**（構造としての説明）
> 【Typical】技術者にとって、プログラムを書くことが仕事です。工数の入力は「事務作業」に見えます。
> 入力しなくてもその日の仕事は終わります。**困るのは後になってからです。**
> そのため、PMは日次で入力状況を確認する運用をとります（05の③-4・④-8）。
> **本資料は、この運用の良し悪しを評価しません。**

### ⑪ 進捗情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 「予定に対して、いまどこまで進んでいるか」 |
| **具体的に何が入っているか** | WBS（作業を分解し、担当と期日を置いた表）の予定と実績、遅れの理由、対策、**着地見込み** |
| **誰が作るか** | PM |
| **誰に渡すか** | 社長（社内報告）、**顧客**（週次の進捗会議・進捗報告書） |
| **何を決めるために使うか** | **間に合うかどうか／人を足すか／顧客と納期を協議するか** |
| **記録しないと何が困るか** | 【Typical】「だいたい順調です」という報告だけになり、**遅れが表に出るのが遅くなります** |
| **頻度** | **週次**（社内・顧客への報告）／日次（PMの確認） |

> **★進捗情報と作業実績情報は別のものです**
>
> | | 進捗情報 | 作業実績情報（工数） |
> |---|---|---|
> | 何を表すか | **どこまで終わったか** | **どれだけ時間を使ったか** |
> | 誰が記録するか | PM（担当者の報告をまとめる） | 技術者本人 |
> | 食い違う例 | 「50%完了」 | 「見積の80%の工数を消費」 |
>
> **この2つを突き合わせると、遅れが見えます。**
> 「50%しか終わっていないのに、工数は80%使っている」＝**このままいくと大幅に超過する**、という予測になります。

## 9-4. ★仕様変更の記録——言った言わないを防ぐ

### (1) 仕様変更情報（⑫）

| 項目 | 内容 |
|---|---|
| **何の情報か** | 契約後に、顧客から出た「これも追加してほしい」「ここを変えたい」という要望と、その扱いの合意 |
| **どこから来るか** | 顧客（担当者・窓口）、【Varies】常駐先の現場の会話 |
| **誰が受け取るか** | PM（または現場のSE） |
| **どこに記録するか** | **変更管理書（変更提案書）**、**課題一覧**、議事録 |
| **誰が判断するか** | **PM**（影響の判定）→ **社長**（受けるかどうかの決定）→ **顧客**（合意） |
| **何を決めるために使うか** | **★追加費用を請求できるかどうか／納期を変えるかどうか** |
| **頻度** | 案件発生時 |

### (2) なぜ記録が必要なのか

```
  【記録がある場合】
    顧客の要望 ──▶ PMが影響を判定（追加1.2人月、納期+26日）
                    ──▶ 変更管理書を発行 ──▶ 顧客が承認
                    ──▶ 契約金額が 1,122.5万円 → 1,224.5万円 に変更
                    ──▶ ★追加費用102万円を請求できる

  【記録がない場合】
    顧客の要望 ──▶ 現場のSEが「そのくらいならやっておきます」
                    ──▶ 1.2人月（約58万円の原価）が発生
                    ──▶ ★請求できない。自社負担になる
                    ──▶ しかも、記録がないので「なぜ超過したか」も分からない
```

> **04の4-6は次のように述べています。**
> **「口頭で引き受けた変更は、記録に残らず、費用も回収できません。」**

### (3) 変更管理書に書くこと【Typical】

| 項目 | なぜ書くのか |
|---|---|
| 変更の内容 | **何を追加・変更するのか**を特定するため |
| 変更の理由・依頼者 | 誰の要望かを残すため |
| **追加工数** | いくら追加費用がかかるかの根拠 |
| **追加金額** | 請求の根拠 |
| **納期への影響** | 元の納期で終わらないことを合意するため |
| 影響する成果物 | 設計書のどの版を直すかを特定するため |
| **双方の承認** | **合意したことの証拠**。これがないと請求できない |

【Fact】IPA・経済産業省のモデル契約も、変更管理の手続きを条文（第34条）で定めています
（出典：情報システム・モデル取引・契約書〈第二版〉／IPA・経済産業省。02の11-3で引用）。

### (4) ★記録されるべき「もう1つの言った言わない」

【Typical】仕様変更のほかに、**顧客の作業の遅れ**も記録の対象になります。

| 何を記録するか | どこに記録するか | 何のために |
|---|---|---|
| **顧客への質問と、その回答期限** | 課題一覧（課題管理表） | 【Typical】回答が遅れて作業が止まった場合、<br>**その期間を記録として残すため** |
| **顧客の承認の日付** | 議事録、承認記録 | 「いつ承認されたか」を特定するため |
| **顧客側の作業の予定と実績** | プロジェクト計画書、WBS | 【Typical】顧客が用意するはずのデータや環境が遅れた場合の記録 |

> **【Example】05の5-15の振り返りの例**（説明用の架空例）
>
> | 超過の原因 | 人月 | 誰が負担したか |
> |---|---:|---|
> | 顧客の業務が想定より複雑だった（見積の甘さ） | 1.2 | **自社** |
> | 既存システムの資料が古く調査に時間がかかった | 0.7 | **自社**（前提条件書に記載がなかった） |
> | 顧客の回答が遅れた | 0.6 | **自社**（記録はあるが交渉しなかった） |
> | 仕様変更（変更管理書で合意済み） | 1.4 | **顧客**（別途150万円を請求） |
>
> **記録があっても交渉しなければ自社負担になります。** 記録は交渉の前提であって、交渉そのものではありません。

## 9-5. ★顧客から預かる情報の管理

### (1) 何を預かるのか

07の7-6で見たとおり、この業界では顧客の業務の中身に深く触れます。

| 預かる情報 | いつ | 何のために |
|---|---|---|
| 業務資料（帳票の見本、手順書、**価格表**） | ②ヒアリング／⑨要件定義 | 何を作るかを決めるため |
| **既存システムのデータ**（受注履歴、商品マスタ、**取引先一覧**） | 移行作業 | データ移行のため |
| **テスト用のデータ** | ⑫テスト | 本番に近い状態で確かめるため |
| **本番のデータ**【Varies】 | ⑰運用・保守（障害調査） | 原因を調べるため |
| **顧客の社内の事情**（誰が何を決めるか、部門間の関係） | 常時 | 合意を取り付けるため |

> **【Typical】この業界の仕事は、顧客の業務の中身を深く知ることから始まります。**
> 顧客の売上構成、原価の計算方法、取引先の一覧、価格表といった情報に触れることになります。

### (2) 秘密保持契約（NDA）

**NDA（エヌディーエー）／秘密保持契約**
→ Non-Disclosure Agreement の略。「仕事で知った相手の情報を、外に出さない」ことを約束する契約。
→ 実務例：見積のために顧客の業務資料を受け取る前に結ぶ。
   【Typical】商談の一番最初に結ぶことが多い。

| 確認する項目 | なぜ確認するか |
|---|---|
| **何が秘密情報にあたるか**（範囲の定め方） | 範囲が広すぎると、自社の通常業務も制約されます |
| **秘密保持の期間**（契約終了後何年か） | いつまで守る義務があるかを知るため |
| **誰に開示できるか**（**協力会社に渡せるか**） | **渡せないと、協力会社を使えません**（05の⑧-6の外注ができない） |
| **返還・廃棄の義務** | **成果物は複製できるため**（07の7-1(3)）、「消す」約束が必要になります |
| 自社が負う義務と、相手が負う義務が対等か | 一方的な内容になっていないかを見るため |

> **★協力会社への開示の可否が、実務上とくに重要です**
> 【Typical】秘密保持契約に「第三者への開示を禁止する」と書かれていると、
> **協力会社の技術者にその情報を見せることができません。**
> つまり、外注ができなくなります。
>
> そのため実務では、「**事前の書面による承諾を得た場合は、同等の秘密保持義務を負わせたうえで開示できる**」
> といった形にしておく必要があります【Typical】。
> この確認を怠ると、受注後に「協力会社を使えない」ことが判明し、要員のアサインが組めなくなります（05の⑪-5）。

### (3) 個人情報が含まれる場合

【Fact】
> **個人情報の保護に関する法律 第二十五条（委託先の監督）**
> 「個人情報取扱事業者は、個人データの取扱いの全部又は一部を委託する場合は、
> その取扱いを委託された個人データの安全管理が図られるよう、
> **委託を受けた者に対する必要かつ適切な監督を行わなければならない**。」
> （出典：個人情報の保護に関する法律／e-Gov法令検索）

**条文の文言でいえば**、監督の義務を課しているのは「**委託する側**」です。

**実務上の意味（条文の説明ではなく、実務としてどうなるか）**
【Typical】顧客が個人データの取扱いを自社に委託する場合、**顧客がこの義務を負います。**
その結果として、**委託を受ける側（自社）に対して、取り扱いのルールの遵守や報告が求められます**（05の⑪-8）。

【Typical】具体的には、次のような形で現れます。

| 求められること | どの機能が対応するか | 頻度 |
|---|---|---|
| 顧客が定めたセキュリティ基準への同意 | ⑪契約・法務 | 案件発生時 |
| 作業場所・保管場所の制限（**持ち帰り禁止**、指定された環境でのみ作業） | ③PM／④開発／⑦インフラ | 常時 |
| **アクセスできる人を限定し、その一覧の提出** | ⑦インフラ（アカウント一覧） | 案件発生時／月次（点検） |
| **作業終了後の削除の証明** | ③PM／⑦インフラ | 納品時 |
| 状況の報告 | ③PM／⑥運用・保守 | 月次／四半期【Varies】 |

### (4) 自社の中での情報の扱い

| 何を | どう扱うか【Typical】 |
|---|---|
| **顧客から受け取ったファイル** | 案件ごとに保管場所を分け、**関係者だけがアクセスできるようにする** |
| **アカウントと権限** | 誰がどの環境に入れるかを一覧で管理し、**離任時・退職時に削除する**（05の⑦-3） |
| **持ち出し** | 【Varies】顧客の方針による。**持ち帰り禁止の現場では、自社に情報を持ち出せない** |
| **人事関係の書類** | 施錠できる場所に保管する（個人情報を扱うため。05の⑨のN項） |

## 9-6. ★常駐先での情報の扱い【Varies】

### (1) 常駐者は「2つの会社の情報」の間にいる

【Example】モデル企業では技術者40名のうち19名が常駐しています（03の3-2）。
常駐者は、**常駐先の情報に日々触れながら、自社の社員として働いています。**

```
  【自社の情報】                        【常駐先の情報】
  ・自社の給与・評価                    ・常駐先の業務データ
  ・自社の案件情報                      ・常駐先の顧客（エンドユーザー）の情報
  ・自社の見積・単価                    ・常駐先の社内ルール
  ・他の顧客の情報                      ・常駐先のシステムの中身
        │                                      │
        └────────── 常駐している技術者 ─────────┘
                       この人の中で交わる
```

### (2) 常駐先で守ることになる決まり【Varies】

【Typical】常駐先では、その会社の情報管理のルールに従うことになります。
**どこまでが求められるかは、常駐先の業種・規模・方針によって大きく異なります**【Varies】。

| よく見られる制限【Typical】 | 内容 |
|---|---|
| **持ち込み機器の制限** | 自社のPC・記録媒体・カメラを持ち込めない |
| **ネットワークの制限** | 常駐先のネットワークからは、外部のファイル共有サービスに接続できない |
| **持ち出しの禁止** | 常駐先で作成したものを自社に持ち帰れない |
| **入退館の記録** | 入館証で毎日の出入りが記録される |
| **秘密保持の誓約** | 【Varies】常駐先に対して、個人として誓約書を出すことがある |
| **作業場所の限定** | 指定された席・区画でのみ作業する |

> **★この制限が、自社の業務に跳ね返ります**
> 【Typical】たとえば次のようなことが起きます。
>
> | 制限 | 自社側で起きること |
> |---|---|
> | 常駐先のPCしか使えない | **自社の工数入力の仕組みに、その場でアクセスできない**<br>→ 帰宅後や自社のPCから入力することになる（11で扱う） |
> | 自社のメールが見られない | 自社からの連絡が届くのが遅れる |
> | 持ち出し禁止 | **自社に成果物の控えを残せない** |
> | 入退館記録が常駐先にある | **勤怠を自社と常駐先の両方に付けることになる**（11で扱う） |

### (3) 常駐者が「話してはいけないこと」の方向は2つある

【Typical】秘密保持は、一方向ではありません。

| 方向 | 内容 |
|---|---|
| **常駐先 → 外（自社を含む）** | 常駐先で知った情報を、自社の同僚や他の顧客に話さない |
| **自社 → 常駐先** | **自社の他の顧客の情報**を、常駐先で話さない |

> **【Example】説明用の架空例**
> P社に常駐している技術者が、「前の現場（Q社）では、こういう仕組みで作っていました」と話した。
> → その「仕組み」がQ社の秘密情報にあたる場合、**Q社との秘密保持契約に反することになります。**
>
> 【Typical】そのため、常駐開始時の説明（自社のリーダーが行う）で、この両方向を伝える運用がとられます。

### (4) 情報の扱いと、指揮命令の論点は別のもの

> **★混同しやすいので、ここで分けておきます。**

| | 情報の扱い | 指揮命令（06の6-6） |
|---|---|---|
| 何の問題か | **秘密保持と個人情報の取り扱い** | **告示37号の基準（労働者派遣事業か否か）** |
| 根拠 | 秘密保持契約／個人情報保護法第25条に基づく顧客の監督 | 労働者派遣事業と請負により行われる事業との区分に関する基準（昭和61年労働省告示第37号） |
| 常駐先が行ってよいこと | **情報管理のルールを示すこと**（服務上の規律とは区別して整理される） | — |
| 常駐先が行うと論点になること | — | **個々の技術者への作業指示・残業の指示・配置の決定** |

> 【Fact】なお、告示37号第二条第一号ハ1は
> 「労働者の**服務上の規律に関する事項についての指示その他の管理**を自ら行うこと」を挙げています
> （出典：労働者派遣事業と請負により行われる事業との区分に関する基準／厚生労働省）。
> **本資料は、個別の現場における運用がこの基準にどう当てはまるかの判断は行いません。**
> **2つの異なる論点が同じ現場で同時に存在する**ことを押さえてください。

## 9-7. お金になるまでの情報——⑬〜⑮

### ⑬ 検収情報★

| 項目 | 内容 |
|---|---|
| **何の情報か** | 顧客が「合格」と判定したという情報 |
| **どこで生まれるか** | **顧客の中**（社外）。自社は作れません |
| **どんな書類になるか** | **検収合格書（検査合格書）** |
| **誰に渡るか** | 顧客 → PM → **経理** |
| **何を決めるために使うか** | **★請求できるかどうか／いつ売上を計上するか** |
| **記録がないと何が困るか** | **請求書を出せません。** 出しても、根拠がないため支払われません |
| **頻度** | 納品時 |

> **★検収情報は、社外からしか来ません。**
> 自社の誰も、この情報を作れません。**これが請負の構造です**（08の8-2）。

### ⑬' 作業報告の承認情報（準委任の場合）★

| 項目 | 内容 |
|---|---|
| **何の情報か** | その月に何日・何時間働いたかを、顧客が確認したという情報 |
| **どんな書類になるか** | **作業報告書（稼働報告書）**への顧客の承認 |
| **誰が作るか** | 技術者本人（記入）→ 常駐先の主任担当者（確認・承認） |
| **誰に渡るか** | 現場 → **経理** |
| **何を決めるために使うか** | **★請求できるかどうか／請求金額はいくらか**（精算幅の上限・下限） |
| **頻度** | **月次**（月末〜月初に集中する） |

> 04の4-3②が述べているとおり、これは**民法第645条（受任者による報告）の報告義務を実務の形にしたもの**といえます。

### ⑭ 請求情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 顧客にいくら請求するか |
| **具体的に何が入っているか** | 請求先、請求金額（税抜・消費税・税込）、請求日、支払期日、明細（案件名・作業期間） |
| **誰が作るか** | 経理担当 |
| **何を根拠に作るか** | **請負：検収合格書／準委任：承認された作業報告書** |
| **誰に渡すか** | 顧客 |
| **何を決めるために使うか** | いくら受け取るか／いつ入金されるか |
| **頻度** | **請求時**（月次のサイクルで行う） |

### ⑮ 入金情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 顧客から実際にいくら振り込まれたか |
| **どこから来るか** | 銀行の取引照会 |
| **誰が確認するか** | 経理担当 |
| **何をするか** | **消込**（請求と入金を1件ずつ突き合わせて、回収済みにする） |
| **何を決めるために使うか** | **売掛金が回収できたか／督促が必要か／資金繰りの見通し** |
| **記録しないと何が困るか** | **回収できていない請求に気づけません**（05の⑩-5・⑩-6） |
| **頻度** | **入金時**／月次（売掛金の残高確認） |

**消込（けしこみ）**
→ 請求した金額と、入金された金額を1件ずつ突き合わせて、「この請求は回収済み」と印を付ける作業のこと。
→ 実務例：「R社の1月分、消込できました」＝「R社への1月分の請求が入金されたことを確認した」という意味。
   **金額が一部だけ入っていたり、複数の請求がまとめて振り込まれたりするため、突き合わせが必要になります。**

## 9-8. 納めたあとの情報——⑯⑰

### ⑯ 障害情報

| 項目 | 内容 |
|---|---|
| **何の情報か** | 稼働中のシステムに異常が起きたという情報 |
| **どこから来るか** | **顧客からの連絡**／**監視の仕組みからの自動通知** |
| **誰が受け取るか** | 運用・保守担当 |
| **具体的に何が入っているか** | いつ起きたか、何が起きているか、**誰が困っているか**、業務にどんな影響があるか |
| **何を決めるために使うか** | **どれくらい急ぐか（優先度）／誰が対応するか／顧客にいつ報告するか** |
| **頻度** | **トラブル発生時** |

> **★最初に確認するのは「業務が止まっているか」です**
> 【Typical】同じ「動かない」でも、次で優先度が変わります。
> - 業務全体が止まっている → **最優先**
> - 一部の機能が使えないが、回避方法がある → 次
> - 表示が崩れているだけ → 後回し【Varies】
>
> そのため、障害情報には「**業務にどんな影響があるか**」が含まれている必要があります。

### ⑰ 対応記録

| 項目 | 内容 |
|---|---|
| **何の情報か** | その障害・問い合わせに、誰がいつ何をしたかの記録 |
| **どんな書類になるか** | **障害報告書**（発生・影響・原因・対応・再発防止）、**問い合わせ管理表（受付票）**、**既知の不具合一覧** |
| **誰が作るか** | 運用・保守担当 |
| **誰に渡すか** | **顧客**（報告）、開発機能（同じ問題を繰り返さないため） |
| **何を決めるために使うか** | **同じことが起きたときの手がかり／顧客への説明／保守契約の更新の材料** |
| **記録しないと何が困るか** | 【Typical】**同じ問い合わせに毎回ゼロから調べることになります。**<br>また、「先月も同じことが起きた」という事実に気づけません |
| **頻度** | **トラブル発生時**／**問い合わせ時**／月次（稼働報告書にまとめる） |

> **★対応記録は、次の売上につながることがあります**
> 【Typical】対応記録に「この処理が遅い」「この画面が使いにくいという声が多い」という情報が積み上がると、
> 改修の提案材料になります（05の⑥-9）。
> **本資料は改善の提案そのものを扱いませんが、情報がそういう形で使われる**ことは事実として押さえてください。

## 9-9. 情報が社内をどう巡るか（3つの循環）

### 循環① 見積 → 実績 → 次の見積

```
  ③ 工数見積情報（14.6人月と見積る）
        │
        ▼
  ⑩ 作業実績情報（実際は18.5人月かかった）
        │
        ▼
  案件別損益（粗利率36.8%の見込みが、実際は17.1%）
        │
        ▼
  ③-11 振り返り（超過の原因を分類する）
        │
        ▼
  ③ 次の工数見積情報へ反映
      「要件定義は設計・開発の15%ではなく20%に置く」
      「この顧客のバッファを10%から15%に上げる」
```

> **この循環が回っていない会社では、同じ見積の間違いを繰り返します。**
> 循環を回すのに必要なのが、**⑩作業実績情報**です。

### 循環② 引合い → 受注 → 要員 → 引合い

```
  ① 引合い情報（案件がある）
        │
        ▼
  要員の空き状況（人を出せるか）
        │
        ▼
  ⑤ 契約情報（受注する）
        │
        ▼
  要員がふさがる
        │
        ▼
  案件の終了予定（1〜2か月前から次を探す）
        │
        ▼
  ① 次の引合い情報へ
```

> **この循環が止まると、待機が発生します**（08の8-6）。

### 循環③ 障害 → 記録 → 改修 → 障害

```
  ⑯ 障害情報（何かが起きた）
        │
        ▼
  ⑰ 対応記録（原因と対応を残す）
        │
        ▼
  既知の不具合一覧／改修要望
        │
        ▼
  ① 引合い情報（改修案件として営業へ）
        │
        ▼
  改修の実施 → ⑯ 障害が減る／新しい障害が出る
```

## 9-10. 情報が止まると、どこが止まるか

| 止まる情報 | 直接止まること | その先で起きること |
|---|---|---|
| **① 引合い情報** | 提案が始まらない | 受注がなくなり、**待機が発生する** |
| **② 要件情報** | 工数を積めない | 見積が出せない／**出しても後で超過する** |
| **③ 工数見積情報** | 金額を出せない | 顧客が発注判断できない |
| **⑤ 契約情報** | 作業を始められない | **始めても請求できない** |
| **⑥ 要件定義書** | 設計に進めない | **検収の基準がなくなる** |
| **⑩ 作業実績情報** | 進捗と採算が見えない | **★赤字に気づかないまま案件が終わる** |
| **⑫ 仕様変更情報** | 追加請求の根拠がない | **★作業だけ増えて、費用を回収できない** |
| **⑬ 検収情報** | **請求できない** | **★入金されない。資金繰りが詰まる** |
| **⑬' 作業報告の承認** | **準委任の請求ができない** | 同上 |
| **⑮ 入金情報** | 回収できているか分からない | 督促できない／**資金繰りの見通しが立たない** |
| **⑰ 対応記録** | 同じ調査を繰り返す | 保守の工数が増え、**保守の粗利が薄くなる** |

> **★この表でもっとも重い2つは、⑩作業実績情報と⑬検収情報です。**
> - **⑩が止まると、儲かっているかどうかが分からなくなります。**
> - **⑬が止まると、1円も請求できません。**

## 9-12. この章のまとめ

### 情報通信業の情報の流れで押さえるべき8点

1. **物理的なモノがないため、記録されない情報は存在しないのと同じ。**
   作りかけのソフトウェアは目に見えません。

2. **情報には16の名前がある。**
   引合い情報／要件情報／工数見積情報／提案・見積情報／契約情報／要件定義書／設計書／ソースコード／
   テスト結果情報／作業実績情報／進捗情報／仕様変更情報／検収情報／請求情報／入金情報／障害情報・対応記録。

3. **★工数の実績が記録されないと、赤字かどうかが分からない。**
   契約金額（契約書）・実績工数（技術者の入力）・原価単価（給与データ）の3つを掛け合わせて初めて採算が出ます。
   **3つは別々の場所にあるため、月次で突き合わせます。**

4. **★仕様変更は記録しないと、費用を回収できない。**
   変更管理書に双方が承認して初めて、追加費用を請求できます。

5. **検収情報は社外からしか来ない。**
   自社の誰も作れません。これが請負の構造です。

6. **準委任では、作業報告書への顧客の承認が検収情報の代わりになる。**
   民法第645条の報告義務を実務の形にしたものといえます。

7. **顧客から預かる情報は、秘密保持契約と個人情報の取り扱いに縛られる。**
   とくに「**協力会社に開示できるか**」が、外注できるかどうかを決めます。

8. **常駐先での情報の扱いは、常駐先の方針によって大きく異なる【Varies】。**
   持ち込み機器・ネットワーク・持ち出しの制限が、自社側の業務（工数入力・勤怠）に跳ね返ります。
