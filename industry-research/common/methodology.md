# methodology.md — 全業界共通の調査方法論

このファイルは本プロジェクトの**憲法**です。すべての Industry Agent / Slide Agent / QA Agent は
作業開始前に必ず本ファイルと `terminology-rules.md` `design-system.md` を読み、全面的に従ってください。

---

## 0. このプロジェクトの目的（絶対に外さないこと）

> **その業界をまったく知らない人が、典型的な日本の中小企業の「仕事・組織・商流・業務・ヒト・モノ・カネ・情報」を
> 体系的に理解し、その業界の会社と会話できる程度の基礎〜実務理解を得ること。**

作るのは **業界・業務理解の教科書** です。

### これは「提案資料」ではない（厳守）

以下は**書いてはいけません**。書いた時点で成果物は不合格です。

- DX施策 / DX成熟度 / デジタル化ロードマップ
- AI活用 / 生成AI活用 / Copilot活用 / RPA活用
- SaaS導入提案 / IT導入提案 / システム刷新案
- 業務改善案 / 課題に対する解決策 / コンサルティング提案
- 「この業務は自動化できる」「ここが非効率」等の評価・提案
- 特定ITベンダーの商品提案
- 「この業界はDXしやすい / しにくい」等の評価

**唯一の例外**：その業界で現在一般的に使われているシステムを、
**「今の仕事を理解するため」**に「それは何のための道具か」として説明することは可。
例：「販売管理システム＝受注・売上・請求・入金の情報を一元的に記録する仕組み」。
その際も、良し悪しの評価・導入推奨は一切書かないこと。

## 1. 対象は「日本国内の中小企業」

- 大企業特有の姿（事業部制、グローバルSCM、フルスペックERP、シェアードサービス等）を
  「一般的な中小企業の姿」として説明しないこと。
- 中小企業では**一人が複数業務を兼務する**のが普通。
- したがって常に次の視点を持つこと：

  > 「この**仕事（機能）**は必ず存在するが、独立した**○○部**が存在するとは限らない」

- 部署名ではなく**機能**で整理し、そのうえで「一般的にこう呼ばれる」部署名を添える。
  - ✕「営業部がある」
  - ○「顧客対応・見積・受注を担う**営業機能**が必要。会社によって営業部／業務部／社長直轄など呼び方は異なる」

### 中小企業の定義（参考）
中小企業基本法上の定義は業種により異なる（製造業その他：資本金3億円以下 or 従業員300人以下、
卸売業：1億円以下 or 100人以下、小売業：5千万円以下 or 50人以下、サービス業：5千万円以下 or 100人以下）。
各業界ファイルで中小企業の範囲に触れる場合は、この定義を出典付きで正確に引くこと。

## 2. 情報源の優先順位

1. 日本政府・官公庁（中小企業庁、経済産業省、国土交通省、厚生労働省、農林水産省、総務省 等）
2. e-Stat 等の政府統計（経済センサス、工業統計、商業動態統計 等）
3. 各省庁の白書・ガイドライン（中小企業白書、ものづくり白書 等）
4. 独立行政法人・公的機関（中小機構、JETRO、日本政策金融公庫、IPA 等）
5. 業界団体（各工業会・協会・組合）
6. 法令・制度の公式情報（e-Gov法令検索、各省庁の制度ページ）
7. 企業の公式資料（有価証券報告書、IR、公式サイト）
8. 信頼性の高い調査会社・金融機関（帝国データバンク、東京商工リサーチ、各行シンクタンク）
9. 専門メディア（業界紙）
10. その他

### 禁止
- ブログ・SEO記事・まとめサイト**だけ**を根拠に重要事項（統計・制度・法規制・金額）を断定すること。
- 出典URLの捏造。**実際にアクセスして確認したURLのみ**記載すること。
- 年度不明の統計を「最新」として提示すること。

### 調査ツール（403 の回避方法は `common/base-statistics.md` §3 を必ず参照）
**官公庁サイト（meti.go.jp 等）は WebFetch だと 403 になります。Bash の curl にブラウザUAを付けて取得してください。**
共通の基礎統計（産業別企業数・中小企業の定義）は `common/base-statistics.md` に集約済みなので再調査しないこと。

`WebSearch` / `WebFetch` は遅延ロードされている場合があります。使う前に
`ToolSearch` で `select:WebSearch,WebFetch` を読み込んでください（1回のコールでまとめて）。

## 3. 情報の確度タグ（必須）

すべての記述に、可能な限り次のタグを付けてください。
特に**数値・制度・法規制には必須**です。

| タグ | 意味 | 使いどころ |
|---|---|---|
| `【Fact】` | 統計・制度・公的情報等で確認でき、出典を示せる | 市場規模、事業所数、法定義務、資格要件 |
| `【Typical】` | 業界で一般的・典型的とされる業務の姿 | 「見積提出後に注文書を受け取るのが一般的」 |
| `【Example】` | 理解のための**架空**の例 | 「例：部品1,000個の注文を受けた場合」 |
| `【Varies】` | 企業・業態・規模により大きく異なる | 「独立した品質保証部の有無は企業により異なる」 |
| `【Inference】` | 資料から合理的に推定した内容 | 「以上より、〜と考えられる」 |

### 数値の扱い（重要）
- `【Fact】` の数値には**必ず**「年度」と「出典」を併記する。例：`【Fact】製造業の事業所数は約○万（2021年経済センサス／総務省・経産省）`
- 架空の金額・人数例は**必ず** `【Example】` を付け、「説明用の架空例であり実データではない」と明記する。
- 「毎週月曜日に行う」のような**根拠のない具体化は禁止**。頻度は §5 の分類語を使う。
- 確信が持てない数値は**書かない**。推測で埋めず、追加調査するか `【Varies】` として質的に記述する。

## 4. 業界粒度の二層構造（必須）

業界名は粒度が粗いことが多い（例：「製造業」には食品製造も金属加工も印刷も含まれる）。
したがって各業界ファイルは必ず次の二層で整理してください。

- **Level 1：業界共通構造** — その業界全般で比較的共通する構造・機能・流れ
- **Level 2：主要業種による違い** — 「A業種とB業種ではここが決定的に違う」

**業種差が大きい内容を、業界全体の共通事項として断定しないこと。**
Level 2 は最低3〜5業種を取り上げ、「どの軸で違うのか」（受注形態／在庫の持ち方／
リードタイム／規制／顧客／課金方式 等）を明示して比較すること。

## 5. 業務頻度の共通分類（この語彙のみ使用）

```
常時 / 日次 / 週次 / 月次 / 四半期 / 半期 / 年次
案件発生時 / 問い合わせ時 / 受注時 / 発注時 / 納品時 / 請求時 / 入金時
トラブル発生時 / 法定・契約上のタイミング / その他
```

- 企業差が大きい場合は「企業により異なる」と明記（`【Varies】`）。
- 曜日・日付レベルの具体化は、法定期限など根拠がある場合のみ可
  （例：「源泉所得税の納付は原則翌月10日まで＝法定・契約上のタイミング」`【Fact】`）。

## 6. 4つの流れの定義（全業界で統一）

| 流れ | 何を追うか | 書き方の要点 |
|---|---|---|
| **ヒト** | 誰が誰と関わるか／誰が判断・承認・実行するか | 社内関係＋社外関係。簡易RACI（実行・承認・相談・報告）を初心者向けに |
| **モノ** | 物理的なモノがどこから入り、どこで変化し、どこで保管され、どこへ出るか | 物理的なモノが主要でない業界（サービス業等）は**無理に作らない**。代わりに「何が価値の実体か」を書く |
| **カネ** | 見積→契約→売上→仕入／外注費／人件費→請求→売掛金→入金→買掛金→支払→利益 | 会計初心者に分かる言葉で。**時間差（締め支払い等）**を必ず説明 |
| **情報** | 具体的に**何の情報**か | 「情報」という抽象語で終わらせない。「問い合わせ情報」「見積情報」「受注情報」「計画情報」「実績情報」のように命名する |

## 7. 部署別業務の必須15項目（A〜O）

`05_departments.md` では、**すべての主要部署・機能について**以下15項目を欠かさず記述すること。
ここが本プロジェクトの最重要パートです。1項目でも欠けたら不合格。

```
A. 部署・機能名（正式名称・一般的な別名称）
B. 存在目的（初心者向けに1〜3文。「何のために存在するのか」）
C. 担当者（代表的な役職・担当）
D. 主な業務一覧（MECEに近い形で洗い出す）
E. 業務詳細（各業務について以下すべて）
     - 何をきっかけに始まるか
     - 誰が行うか
     - 何を確認するか
     - 何をするか
     - 何を判断するか
     - 誰と連携するか
     - 最終的に何が出来上がるか
F. 業務頻度（§5の分類語）
G. インプット（業務を始めるために必要なもの）
H. アウトプット（業務の結果できあがるもの）
I. 関係部署（前工程・後工程を含む）
J. 社外関係者（顧客・仕入先・外注先・行政等）
K. 使用帳票（業界固有のものを優先）
L. 使用データ（何の情報を扱うか）
M. 使用システム（一般的なシステム種別。商品名の列挙が目的ではない）
N. 使用設備・道具（業界理解に必要な場合）
O. 見ている数字・KPI
```

対象とする部署・機能は最低限：**営業／受注・業務管理／調達・仕入／主業務（製造・施工・提供等）／
品質・安全／物流・出荷／経理・財務／人事・総務** を基本とし、業界固有の機能を追加すること。

## 8. 文章ルール（初心者向け）

読み手は**業界未経験者**です。専門家向けの省略は禁止。

- 専門用語は必ず **専門用語 → 日本語で簡単に説明 → 実務例** の順。
  - ✕「BOMを基にMRPを回す。」
  - ○「製品を作るのに必要な部品の一覧（BOM：部品表）をもとに、いつ・何を・どれだけ仕入れる必要があるかを
     計算します（MRP：資材所要量計画）。たとえば〜」
- **「なぜ？」を必ず書く。** 「検査をする」で終わらせない。
  - ✕「生産管理は生産計画を作成する」
  - ○「受注した製品を納期までに作るため、必要数量・設備・人員・材料・納期を考慮して、
     いつ何を作るかを決めます。これがないと、材料が間に合わず納期遅れが発生します」
- 抽象説明が続いたら **架空の具体例** を入れる（必ず `【Example】` と明記）。
- 一文は短く。受け身より能動。主語（誰が）を省略しない。

## 9. 全体の構造（マクロ→ミクロ）

資料全体を次の順にズームさせること。章立ての順番はこの思想に従う。

```
業界 → 商流 → 会社 → 全社業務 → 部署 → 部署内業務 → 部署間連携
   → ヒト・モノ・カネ・情報 → 帳票・システム → お金 → 定期業務 → KPI → ルール・商習慣 → 用語
```

各業界の違いを尊重し、**共通テンプレートに無理やり当てはめない**こと。
その業界に存在しない項目は「存在しない／該当しない」と理由付きで書く（空欄で放置しない）。

## 10. 出典管理

`19_sources.md` に、使用したすべての出典を次の形式で記録すること。

```
- source_title   : 資料名
  organization   : 発行元
  url            : URL（実際にアクセスしたもののみ）
  published_date : 公表日・年度（不明なら「不明」と明記）
  accessed_date  : 2026-09-16
  used_for       : この資料のどの記述の根拠か
```

本文中では `（出典：中小企業白書2024／中小企業庁）` のような短縮表記を使い、
詳細は `19_sources.md` に集約する。

## 13. 最終品質基準（自己評価10問）

成果物完成時、次の10問すべてに「答えられる」状態か自己評価すること。
1つでも不十分なら該当箇所を補強する。

1. 業界を知らない人が「この業界は何をしているの？」に答えられるか
2. 「この会社はどうやってお金を稼いでいるの？」に答えられるか
3. 「顧客から仕事が来てから入金されるまで何が起きる？」に答えられるか
4. 「どんな部署・担当者がいる？」に答えられるか
5. 「各担当者は具体的に何をしている？」に答えられるか
6. 「その業務はいつ・どの程度の頻度で行う？」に答えられるか
7. 「部署と部署の間で何が渡される？」に答えられるか
8. 「ヒト・モノ・カネ・情報はどう動く？」に答えられるか
9. 「現場ではどんな書類・データを扱う？」に答えられるか
10. 「初心者が業界関係者との会話についていける程度の用語が理解できるか？」

## 14. 最優先事項

**網羅性**と**初心者の理解**。
ただし情報量を増やすこと自体を目的にしない。
「何をするか」だけでなく、
**なぜするのか／誰がするのか／いつするのか／何を受け取るのか／何を作るのか／次に誰へ渡すのか**
まで明確にすること。
